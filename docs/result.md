自然言語 → サービス選定 → API 選定 → 実行 → 結果解釈 → 自然言語応答 の一連の流れが、
**16GB のローカル GPU 上のモデルで成立した。**

しかも成立に大型モデルは要らなかった。

## 2. 主要な判断とその根拠

### 2.1 モデルは 12B 級で足りる

Gemma 4 12B が 40/40。Qwen3.6-35B-A3B (IQ4_XS / IQ3_S) と同等かそれ以上で、
**平均ステップ数が最少 (2.9) でキャッシュ率が最高 (93%)** だった。

35B-A3B は active 3B の MoE なので、総パラメータの大きさは
このタスク (Tool 選定と引数抽出という精度タスク) には効いていない。

→ **「精度が足りなければモデルを大きくする」より先に、Tool 設計・プロンプト・
Projection を詰めるべき**という §21 の方針は、実測でも正しかった。

### 2.2 ルーティングは 1 段階を既定にする (504 Tool まで検証済み)

2 段階 (サービス選定 → Tool 選定) は精度を上げなかった。上げたのはコストだった。

| 構成 | prompt tok | cache 率 |
|---|--:|--:|
| one_stage (全 24 Tool 固定) | 1548 | **95〜97%** |
| two_stage | 957〜1049 | 70〜77% |

`one_stage` は system prompt が常に同一なので prefix 全体がキャッシュに乗る。
`two_stage` は Stage 2 の Tool 一覧が Stage 1 の出力で変わるため、
**要求ごとに prefix が変わってキャッシュが効かない**。往復も 1 回増える。

→ 元案 §16 の「段階的絞り込みで context を減らす」は、prefix cache のある環境では
**トークン数は減るが実効コストは下がらない**。Tool 一覧がキャッシュに乗らない規模に
なって初めて意味が出る。

### 2.3 権限伝播は初日から入れて正解だった

40 ケースすべてで期待どおりの権限差が観測された。

同一クエリ「田中という名前の顧客を探して」の実測:

| ユーザー | 結果 |
|---|---|
| `u_admin` | 田中太郎 (EAST) と田中次郎 (WEST) の 2 件 |
| `u_sales_e` | 田中太郎 (EAST) のみ |
| `u_sales_w` | 田中次郎 (WEST) のみ |
| `u_wh` | 403。「顧客情報はロール warehouse に参照権限がないため取得できませんでした」 |

**READ-only であっても、これがなければ横断検索は権限を無視した情報漏洩経路になる。**
後付けは Executor と全 Tool 定義の改修になるので、初日に入れた判断は正しかった。

### 2.4 制約デコードが生命線であり、副次的にモデル選択が自由になる

初手 Tool 選定 160 コールで JSON 追従率 100%。`anyOf` で Tool ごとに
引数スキーマを固定する構成も通る。

そして本設計は OpenAI の tools API ではなく `response_format.json_schema` を使うので、
**ネイティブ tool-call 対応のないモデルでも動く**。llama-swap の構成メモで
「tool-call ネイティブハンドラがなく Generic フォールバックになる」とされていた
Gemma 4 12B が最高成績を出したのがその証拠。

## 4. 実測から追加した 5 つの防御

いずれも「スキーマだけでは防げない失敗」を実測してから入れた。

### 4.1 Tool 未実行での `finish` を文法で禁止

初回反復でいきなり `next:"finish"` を選び、何も調べずに「情報がありません」と
答える失敗を観測した。プロンプトで依頼するのではなく、Tool 実行が 1 回成立するまで
`finish` の分岐自体をスキーマから外す。

### 4.2 未解決 ID の差し戻し

IQ3_S の失敗はいずれも **存在しない ID の捏造** (`{"customer_id":"CUST-001"}`) だった。
`strict` スキーマでは防げない。customer_id は正当な string 引数だからだ。

→ ユーザー入力にも過去の Tool 結果にも現れていない ID 値を Executor が検出して差し戻す。

**スキーマで守れるのは「形」だけで、「出所」は Executor が見るしかない。**

### 4.3 曖昧な対象での更新提案を差し戻す

顧客 5,000 件の環境で「山田さんの電話番号を変更して」と言うと、
`customer.search(name=山田)` が 250 件当たり、モデルは**先頭の 1 件を選んで
更新提案を出した**。顧客が 6 件しか無かったときは起きなかった失敗。

読み取りなら誤りは画面で気づける。更新は違う。承認画面には 1 件しか出ないので、
**他に 249 件候補があったという事実が承認者から消える**。

→ 候補が 2 件以上あった一覧に出てきた ID に印を付け、更新提案の引数に
使われたら差し戻す (`executor.AmbiguousIDs`)。1 件に絞り込めた検索の結果は
印を外すので「山田」→ 250 件 → 「山田太郎」→ 1 件 なら通る。
利用者が自分で書いた ID (「C005 の…」) は最初から対象外。

### 4.4 reason の長さを文法で縛る

結果集合が大きいとき、モデルは `reason` (自由記述) の中へ取得した行を
全部書き出そうとして `max_tokens` に達し、JSON が閉じないまま落ちた (171 件中 3 件)。

プロンプトで「短く書いて」と頼むのではなく、スキーマに `maxLength: 120` を入れた。
llama.cpp は JSON Schema の `maxLength` を GBNF に落とすので、
**長く書くこと自体が文法上できなくなる**。512 tok → 99 tok。

READ 側にも同じガードを広げた (2026-09-02)。当初「読み取りは間違えても
画面で気づける」として更新だけに入れたが、**文章で返る場合は気づけない**。
「高橋さんの一番古い注文」(高橋は 251 人) で 1 人を黙って選び、
2 年 7 か月ずれた答えを断定形で返す失敗を実測した。

広げる前に既存 177 ケースを解析し、「候補が複数ある ID を読み取りに使う」
ケースが **0/177** であることを確認している (横断検索は必ず 1 件に絞ってから使う)。
差し戻しには候補件数を入れる。件数があると、モデルは候補を列挙して
利用者に選択を求めるところまで自分でやる。

### 4.5 同一呼び出しの繰り返しを差し戻す

小型モデルが同じ Tool を同じ引数で繰り返して進捗しない失敗を観測した
(`customer.search` × 6 で max_steps 到達)。実行済みの (Tool, 引数) を記録し、
2 回目以降は実行せず「結果は上にあります」と差し戻す。

導入後、Qwen3.5 4B の C07 は 6 回 → 2 回に減った。

## 5. 残っている失敗モード

### 5.1 曖昧性 (96%)

180 ケースで唯一残るのは D22「注文 O-1007 の出荷日を教えて」。
受注日しか持たない `order.get` を選んでしまう。
Tool の description をさらに書き分けるか、責務境界そのものを見直す余地がある。

### 5.2 誤った Tool が「成功」したときに捏造値を答える (12%)

間違った Tool を step 1 に強制的に踏ませて回復挙動を測った
([recovery-report.md](recovery-report.md))。

接続不可・404 では汚染ゼロ。**エラーは安全装置として正しく機能している。**
危険なのはダミーが形の整った応答を返した場合で、16 件中 2 件が
「商品 P001 の単価は 90100 です」のように**捏造値を断定形で答えた**。

機序は「サービスに留まること」ではなく「**フィールド名が質問と一致すること**」。
`DECOY-currency-1` のような明らかに異常な値を 2 手見ておきながら疑わず、
`unit_price` という名前が一致した瞬間に採用している。
Tool の description に書いた責務境界は**選定には効いたが、結果の解釈には効いていない。**

構造的な防御 (利用者が指定した ID が根拠に現れないことの検出) は未実装。

### 5.3 頼まれていない絞り込みを足す

~~候補が複数ある中から 1 人を黙って選ぶ~~ → **READ 側の曖昧性ガードで解消**
(4.3 を読み取りへ拡張。`-no-ambiguity-guard` で旧挙動に戻せる)。

残っているのは別の形。「高橋みどりさんの一番古い注文は？」で氏名は 1 件に
絞れているのに、**`status: PLACED` を勝手に足して** SHIPPED の注文を除外し、
O-1009 / 2026-08-27 と答えた (正解は O-1010 / 2026-08-18、2/2 再現)。
並べ替え (`sort=ordered_at_asc`) は正しく使えている。誤りは足した条件のほうにある。

**構造での防止は失敗した。** 根拠を引用させて Executor が照合する機構を作り、
狙ったケースは直ったが、モデルが引用を書けず (設定した引数と違うキーに
`"searching"` のような内部メモを書く)、「西日本の顧客は何件」のような
正当なケースを壊したので撤去した ([decisions.md](decisions.md))。

代わりに**実際に適用された絞り込み条件を画面に出す**ようにした。
回答は誤ったままだが、「一番古い注文」と聞いたのに `status = PLACED` で
絞られていることは人間なら一目で分かる。**緩和であって解決ではない。**

W31 で入れた曖昧性ガードは**更新提案の経路にしか効いていない**。
当時「読み取りなら誤りは画面で気づける」と書いたが、
**文章で返る場合は気づけない**。READ 側のガードは未実装。

### 5.4 過剰探索

答えに十分な情報が揃った後も Tool を呼び続け、`max_steps` に到達する例が残る。
精度は落ちないが往復が無駄になる。

### 5.5 思考 + 制約デコードは Loop で成立しない (harmony 固有ではなかった)

- gpt-oss 20B: 初手 Tool 選定だけなら `reasoning_effort:"low"` で 90〜95%、
  Tool Loop 全体では **12%**。失敗は全て「content が空のまま出力枠を使い切る」
- **当初これを「harmony 形式と制約デコードの相互作用」と推定していた。狭すぎた。**
  Gemma 4 12B で思考を有効にすると**まったく同じ症状**が出る (2026-09-02 実測):

  | | 総合 (59 件) | 平均ms | 失敗の内訳 |
  |---|--:|--:|---|
  | thinking OFF | **98%** | 4,974 | 1 件 |
  | thinking ON (2048) | **78%** | 24,833 | 13 件中 **10 件が content 空** |

- **予算を上げると減るが、消えない。** 落ちた 10 件を倍々で流し直すと
  4096 で 6 件、8192 で 4 件が残る。決定的なのは D15 の単体実行で、
  **`max_tokens=16384` / prompt 992 tok / 234 秒でも content は空**。
  既定の 32 倍を 4 分使って JSON を 1 つも出せない。step 1 なので履歴の伸びは無関係。
- 小さなスキーマ (3 プロパティ) の単発なら 1,453 tok で終わる。
  Loop の実スキーマ (24 Tool + 画面定義の `anyOf`) では終わらない。
  → **文法の複雑さと思考の干渉**が疑わしいが、切り分けは未完了。

「モデルが弱い」という結論ではない。既定は thinking OFF のまま
(`-thinking` で比較可能)。詳細は [decisions.md](decisions.md)。

## 6. 測定上の限界

正直に書いておく。

1. **この章のレイテンシは信用できない。** モデル階段と Tool Loop の測定中は、
   並行してビルドや DB 操作をしていた。ncmoe による CPU オフロード構成は CPU 負荷の影響を受ける。
   精度・トークン数・キャッシュ率は影響を受けない。
   → **Tool 選定のレイテンシだけは後日マシンを空けて測り直した**
   ([scale-report.md](scale-report.md))。Tool Loop 全体のレイテンシは依然として未測定。
2. **n=40 は小さい。** 98% と 100% の差は 1 ケース。読み取ってはいけない。
3. ~~Response Projection の精度への寄与は未検証~~ → **解消。ただし当初の主張は外れた。**
   注文 50,011 件のデータで A/B を取り直した (171 ケース):

   | | 総合 | prompt tok | cache 率 | 平均 ms | LLM 投入 B |
   |---|--:|--:|--:|--:|--:|
   | Projection ON | 99% (170/171) | 5,269 | 85% | 4,154 | 551 |
   | Projection OFF | 99% (169/171) | 10,390 | 58% | 5,020 | 8,371 |

   コストは明確に効く (トークン +97% / キャッシュ 85%→58% / レイテンシ +21%) が、
   **精度は 5 万件でも変わらなかった**。「Projection が無いと小型モデルが破綻する」は
   裏付けられていない。破綻を防いでいるのは**サービス側のページング**のほうで、
   ページングが無ければ生レスポンスは 6.98MB = 約 170 万トークンあり、
   32k context に入らない (精度低下ではなく動作不能)。
   → Projection は一次防御ではなくコスト最適化。詳細は
   [decisions.md](decisions.md) の「データ規模の検証」。
4. ~~Tool 数 24 は少ない~~ → **解消**。504 Tool まで拡大して測定した
   ([scale-report.md](scale-report.md))。ただしバルクのダミーはテンプレート生成で、
   難易度を担うのは手書きの隣接サービス 7 つだけ。実運用で 500 個の Tool が
   全て互いに紛らわしい場合は、この結果より悪くなる。
   ダミー Tool を選んでしまったときの Loop の回復挙動も未検証。

## 7. 次の一手 (優先順)

1. **ゴールデンセットを 40 → 150 件以上に拡大。** 現状は分解能が足りず、
   これ以上の改善が測れない。最優先。
2. **Tool Loop 全体のクリーンなレイテンシ測定。** Tool 選定については実施済みだが、
