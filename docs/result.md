# PoC 判定

## 結論: 成立

自然言語 → サービス選定 → API 選定 → 実行 → 結果解釈 → 自然言語応答 の一連の流れが、
**16GB のローカル GPU 上のモデルで成立した。**

しかも成立に大型モデルは要らなかった。

## 0. 最新の成績 (150 ケース / one_stage / Intent Gate 有効)

ゴールデンセットを 40 → 150 件へ拡充し、画面遷移とステップ数上限を採点に加えた結果。

| モデル | 総合 | 必須Tool | 禁止Tool回避 | 権限 | 遷移 | step超過なし | 平均step | 平均ms |
|---|--:|--:|--:|--:|--:|--:|--:|--:|
| **Gemma 4 12B** | **99%** | 99% | 99% | 100% | 100% | **100%** | **2.4** | 4156 |
| Qwen3.6-35B-A3B IQ4_XS | 83% | 97% | 97% | 100% | 98% | 87% | 3.3 | 4858 |
| Qwen3.5 4B | 82% | 93% | 98% | 98% | 99% | 93% | 3.1 | 1777 |
| Qwen3.6-35B-A3B IQ3_S | 78% | 99% | 99% | 100% | 99% | 79% | 3.8 | 2680 |
| Qwen3.5 9B | 77% | 97% | 95% | 100% | 98% | 82% | 3.8 | 2095 |

**40 件では 100 / 100 / 98 / 98 / 92% でほぼ差が無かった。150 件では 16〜22 ポイント開いた。**

差がついたのは Tool の選定精度ではない。どのモデルも「必須Tool」は 93〜99% で並んでいる。
分かれたのは **step超過なし** (Gemma 100% に対し他は 79〜93%)、つまり
**いつ止めるかの判断**だった。40 件のセットにはステップ上限も exploration ケースも
無かったため、この軸をまったく測れていなかった。

Qwen3.5 4B (82%) が 9B (77%) と IQ3_S (78%) を上回っており、
**モデルサイズと精度が単調でない**という傾向はここでも続いている。

カテゴリ別 (Gemma 4 12B):

| カテゴリ | n | 総合 |
|---|--:|--:|
| navigate | 25 | 100% |
| exploration | 15 | 100% |
| single_tool | 20 | 100% |
| multi_hop | 18 | 100% |
| cross_service | 25 | 100% |
| permission | 22 | 100% |
| ambiguity | 25 | 96% |

唯一の失敗は D22「注文 O-1007 の出荷日を教えて」で `order.get` (受注日しか持たない) を選んだもの。

## 2. 主要な判断とその根拠

### 2.1 モデルは 12B 級で足りる

Gemma 4 12B が 40/40。Qwen3.6-35B-A3B (IQ4_XS / IQ3_S) と同等かそれ以上で、
**平均ステップ数が最少 (2.9) でキャッシュ率が最高 (93%)** だった。

35B-A3B は active 3B の MoE なので、総パラメータの大きさは
このタスク (Tool 選定と引数抽出という精度タスク) には効いていない。

→ **「精度が足りなければモデルを大きくする」より先に、Tool 設計・プロンプト・
Projection を詰めるべき**という §21 の方針は、実測でも正しかった。

### 2.2 ルーティングは 1 段階を既定にする (504 Tool まで検証済み)

2 段階 (サービス選定 → Tool 選定) は精度を上げなかった。上げたのはコストだった。

| 構成 | prompt tok | cache 率 |
|---|--:|--:|
| one_stage (全 24 Tool 固定) | 1548 | **95〜97%** |
| two_stage | 957〜1049 | 70〜77% |

`one_stage` は system prompt が常に同一なので prefix 全体がキャッシュに乗る。
`two_stage` は Stage 2 の Tool 一覧が Stage 1 の出力で変わるため、
**要求ごとに prefix が変わってキャッシュが効かない**。往復も 1 回増える。

→ 元案 §16 の「段階的絞り込みで context を減らす」は、prefix cache のある環境では
**トークン数は減るが実効コストは下がらない**。Tool 一覧がキャッシュに乗らない規模に
なって初めて意味が出る。

### 2.3 権限伝播は初日から入れて正解だった

40 ケースすべてで期待どおりの権限差が観測された。

同一クエリ「田中という名前の顧客を探して」の実測:

| ユーザー | 結果 |
|---|---|
| `u_admin` | 田中太郎 (EAST) と田中次郎 (WEST) の 2 件 |
| `u_sales_e` | 田中太郎 (EAST) のみ |
| `u_sales_w` | 田中次郎 (WEST) のみ |
| `u_wh` | 403。「顧客情報はロール warehouse に参照権限がないため取得できませんでした」 |

**READ-only であっても、これがなければ横断検索は権限を無視した情報漏洩経路になる。**
後付けは Executor と全 Tool 定義の改修になるので、初日に入れた判断は正しかった。

### 2.4 制約デコードが生命線であり、副次的にモデル選択が自由になる

初手 Tool 選定 160 コールで JSON 追従率 100%。`anyOf` で Tool ごとに
引数スキーマを固定する構成も通る。

そして本設計は OpenAI の tools API ではなく `response_format.json_schema` を使うので、
**ネイティブ tool-call 対応のないモデルでも動く**。llama-swap の構成メモで
「tool-call ネイティブハンドラがなく Generic フォールバックになる」とされていた
Gemma 4 12B が最高成績を出したのがその証拠。

## 4. 実測から追加した 3 つの防御

いずれも「スキーマだけでは防げない失敗」を実測してから入れた。

### 4.1 Tool 未実行での `finish` を文法で禁止

初回反復でいきなり `next:"finish"` を選び、何も調べずに「情報がありません」と
答える失敗を観測した。プロンプトで依頼するのではなく、Tool 実行が 1 回成立するまで
`finish` の分岐自体をスキーマから外す。

### 4.2 未解決 ID の差し戻し

IQ3_S の失敗はいずれも **存在しない ID の捏造** (`{"customer_id":"CUST-001"}`) だった。
`strict` スキーマでは防げない。customer_id は正当な string 引数だからだ。

→ ユーザー入力にも過去の Tool 結果にも現れていない ID 値を Executor が検出して差し戻す。

**スキーマで守れるのは「形」だけで、「出所」は Executor が見るしかない。**

### 4.3 同一呼び出しの繰り返しを差し戻す

小型モデルが同じ Tool を同じ引数で繰り返して進捗しない失敗を観測した
(`customer.search` × 6 で max_steps 到達)。実行済みの (Tool, 引数) を記録し、
2 回目以降は実行せず「結果は上にあります」と差し戻す。

導入後、Qwen3.5 4B の C07 は 6 回 → 2 回に減った。

## 5. 残っている失敗モード

### 5.1 曖昧性 (95%)

- 「今年の受注金額」→ `order.getSummary` に到達できず `customer.search` を繰り返す
- 「到着予定日」→ `getDeliveryEstimate` の後に不要な `getTracking` まで踏む

Tool の description をさらに書き分けるか、責務境界そのものを見直す余地がある。

### 5.2 過剰探索

答えに十分な情報が揃った後も Tool を呼び続け、`max_steps` に到達する例が残る。
精度は落ちないが往復が無駄になる。

### 5.3 gpt-oss 20B が Loop で成立しなかった (未解決)

- 初手 Tool 選定だけなら `reasoning_effort:"low"` で 90〜95%
- Tool Loop 全体では **12%**。`max_tokens` を 2048 まで上げても改善しない
- 失敗は全て「reasoning が止まらず content が空のまま出力枠を使い切る」

harmony 形式と制約デコードの相互作用と推定しているが、**切り分けは未完了**。
「モデルが弱い」という結論ではない。

## 6. 測定上の限界

正直に書いておく。

1. **この章のレイテンシは信用できない。** モデル階段と Tool Loop の測定中は、
   並行してビルドや DB 操作をしていた。ncmoe による CPU オフロード構成は CPU 負荷の影響を受ける。
   精度・トークン数・キャッシュ率は影響を受けない。
   → **Tool 選定のレイテンシだけは後日マシンを空けて測り直した**
   ([scale-report.md](scale-report.md))。Tool Loop 全体のレイテンシは依然として未測定。
2. **n=40 は小さい。** 98% と 100% の差は 1 ケース。読み取ってはいけない。
3. **Response Projection の精度への寄与は未検証。** Projection を切っても総合 100% のまま、
   prompt トークンが 6728 → 8244 (+23%)、キャッシュ率が 87% → 80% に落ちただけだった。
   結果集合が小さい (最大 20 件) ためで、**大きな結果集合での効果は測れていない。**
   現時点で言えるのは「コスト削減効果は約 80%」までで、
   「小型モデルが破綻する」という当初の主張は**まだ裏付けられていない**。
4. ~~Tool 数 24 は少ない~~ → **解消**。504 Tool まで拡大して測定した
   ([scale-report.md](scale-report.md))。ただしバルクのダミーはテンプレート生成で、
   難易度を担うのは手書きの隣接サービス 7 つだけ。実運用で 500 個の Tool が
   全て互いに紛らわしい場合は、この結果より悪くなる。
   ダミー Tool を選んでしまったときの Loop の回復挙動も未検証。

## 7. 次の一手 (優先順)

1. **ゴールデンセットを 40 → 150 件以上に拡大。** 現状は分解能が足りず、
   これ以上の改善が測れない。最優先。
2. **Tool Loop 全体のクリーンなレイテンシ測定。** Tool 選定については実施済みだが、
   Loop 全体 (複数往復 + 最終回答生成) はまだ汚れた条件でしか測っていない。
3. ~~Tool 数を 24 → 100 以上へ拡大~~ → **実施済み (504 Tool まで)**。
   Gemma 4 12B は 504 Tool でも 100%、Qwen3.6-35B-A3B は 90% まで低下
   ([scale-report.md](scale-report.md))。Retrieval は Tool 数のためではなく
   モデルの精度を補うために検討する対象になった。
   Projection の効果は依然として大きな結果集合で測り直す必要がある。
4. **過剰探索の抑制。** 「十分な情報が揃ったか」の判定を改善する。
5. **BFF + 最小 UI。** ここまで来たら §3 の構成へ進んでよい。
6. **§14 の UI State 生成。** `route + filters` を返す経路は成功率が高く価値も出やすい。
7. **WRITE の Command Proposal (§13)。** READ-only の基盤が固まった後。
