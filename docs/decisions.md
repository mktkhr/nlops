## 元案からの主な変更

### C1. Response Projection を設計の中心に置く

元案には項目自体がなかったが、実 API の JSON をそのまま context に戻すと小型モデルは破綻する。
Tool 定義ごとに「LLM へ返すフィールドの whitelist」「最大件数」「ネスト展開の深さ」を必須項目とする。

### C2. context 削減は「履歴の後処理」ではなく「Tool Result 追加時点の Projection」で行う

`--cache-reuse 256` が有効なため、prompt prefix をバイト単位で安定させる必要がある。
途中で履歴を要約圧縮すると prefix が壊れてフル再 prefill になり、レイテンシが跳ねる。

Orchestrator が守る制約:

- system prompt と Tool 定義の順序を固定する（map の iteration 順で並べない）
- prefix に現在時刻・ランダム ID・リクエスト ID を入れない
- 履歴は append のみ

### C3. モデル階段は単調ではない

`Qwen3.6-35B-A3B` は active 3B の MoE。総パラメータは 35B だが 1 トークンあたりに通る重みは 3B 相当。
Tool 選定と引数抽出は精度タスクなので、dense `Qwen3-14B Q4_K_M` (active 14B / 4.8bpw) が
`35B-A3B IQ3_S` (active 3B / 3.4bpw) を上回る可能性がある。上限を決め打ちせず測定する。

### C4. ルーティング段数を測定対象に格上げ

PoC 規模（5 サービス / 24 API）では Stage 1 の追加往復がレイテンシを支配しうる。
2 段階を前提とせず、1 段階と同一条件で比較する。

## 保留

- **ceiling の妥当性**: ローカル最大構成で失敗した場合、「アーキが悪い」のか「まだモデルが小さい」のか
  切り分けられない。LLM クライアントを OpenAI 互換インターフェース 1 枚に閉じ込め、切り分けが
  必要になった時点でホスト型モデルへ向けられる状態だけ確保しておく（使うかは後で判断）。

## スケール検証で決着した論点 (2026-08-31, 24〜504 Tool)

元案 §7〜§9 の 2 段階ルーティング (Stage 1 Service Router → Stage 2 Tool Selector) は
**削除してよい**。24〜504 Tool の全域で、`loose` + Executor 検証の 1 段階が
精度・レイテンシとも 2 段階以上だった。

前提だった「全 API 定義を context に入れられない」は prefix cache のある環境では成立しない。
Tool 定義は約 48 tok/Tool で線形に増えるが (504 Tool = 24,363 tok)、
system prompt が固定である限り prefill はキャッシュが吸収する。
**`loose` なら 124 → 504 Tool でレイテンシが +7% しか増えない。**

代わりに効いてくるのは 2 つ。

1. **`anyOf` 分岐の GBNF 文法コスト** — 124 Tool で +30%、504 Tool で **+111〜123%**。
   Executor 側の検証 (`invalidEnums` / `sanitizeArgs`) へ逃がせる。
2. **モデルの限界** — Gemma 4 12B は 504 Tool でも 100%、
   Qwen3.6-35B-A3B は 304 Tool 付近から崩れて 504 Tool で 90%。
   **「何 Tool まで大丈夫か」はアーキテクチャではなくモデルの性質だった。**

詳細は [scale-report.md](scale-report.md)。

## §14 UI State 生成で分かったこと (2026-08-31)

Tool Loop の分岐に `navigate` を 1 つ加えるだけで実装できた。LLM 呼び出しは増えない。
遷移先とフィルタは `catalog/routes.json` に定義したものしか書けないよう `anyOf` で固定する。
Tool Registry と同じ構造を UI ルートへ適用した形。

**速い。** 画面遷移で済む要求は Tool を 1 回も実行しないので、
1.3〜2.0 秒で完了する (Tool 経路は 4〜8 秒)。

### モードの切り替えはプロンプトでは制御しきれなかった

- 画面セクションを Tool セクションの**後ろ**に置くと、`navigate` を一度も選ばなかった (3/3)。
  前に出して判断例を添えたら選ぶようになった。**24 個の Tool 定義に埋もれていた。**
- 「Tool で ID を解決してから navigate する」は、指示を補強しても最後まで再現しなかった。
  **12B モデルはループの途中でモードを切り替えられない。**

### 解決策は「モデルに ID を解決させない」ことだった

画面のフィルタ語彙をユーザーの言葉に合わせる。`/orders` に `customer_name` を足し、
氏名から顧客 ID への解決は BFF の Aggregation で行う。
これで多段の navigate が不要になり、1 ステップで遷移できるようになった。

**LLM に難しい手順を踏ませるより、踏まなくて済むインターフェースを与える方が確実。**

## ゴールデンセット拡充と Intent Gate (2026-08-31)

40 件 → **150 件**へ拡充した (navigate 25 / exploration 15 を新設、既存 5 カテゴリも増量)。
拡充して初めて見えたことが 2 つある。

### 1. §14 は navigate を過剰にも過少にも誤る

40 件のセットでは navigate ケースが 1 つも無く、まったく測れていなかった。
150 件で測ると、プロンプトの書き方次第で両方向に振れた。

| プロンプト | 症状 |
|---|---|
| 画面セクションを Tool の後ろ | navigate を一度も選ばない |
| 画面セクションを前 + 判断例 | 画面が無い領域 (商品・配送業者) でも遷移する |
| 「画面が無いものは Tool」を明示 | 今度は遷移すべき場面で遷移しない (navigate 72%) |

**3 回測って 76% / 76% / 76%。ばらつきではなく一貫した失敗だった。**
プロンプトの往復では収束しない。

### 2. 構造で解いた — Intent Gate

Loop に入る前に「画面を開くだけで満たせるか」を **2 択で 1 回だけ判定**し、
以降の選択肢をその側だけに絞る (`Options.IntentGate`)。
navigate 側なら Tool を一切見せず、tool 側なら画面を見せない。

**27 分岐の中からモードを選ばせるのをやめ、2 択にした。**

| 構成 | navigate 正答 | 全 150 件 |
|---|--:|--:|
| Intent Gate なし | 72% | — |
| Intent Gate あり | **100%** | **99.3%** |

### 3. Gate のコストは 1 リクエスト分の固定費だった

当初「2 つの system prompt が KV キャッシュを奪い合っているのが主因」と書いたが、
**これは誤りだった**。測り直した結果を残しておく。

まず機序の確認。長短 2 つのプロンプトを連続実行と交互実行で比べると:

| 条件 | cache 率 | prefill 合計 |
|---|--:|--:|
| A のみ連続 (6 回) | 99.1% | 678ms |
| B のみ連続 (6 回) | 99.9% | 901ms |
| A/B 交互 (6 回) | 94.0% | 1169ms |

奪い合いは実在するが、コストは 1 ペアあたり約 127ms にすぎない。

次に実際の intent 呼び出しを直接測ると、**連続でも交互でも一貫して約 600ms** だった。
つまりキャッシュ状態と無関係。内訳は 18 トークンの生成で、
制約デコード下では 1 トークンあたり約 33ms (非制約時は約 13ms) かかっていた。

| prompt tok | 生成 tok | wall ms | prefill | 生成 | その他 |
|--:|--:|--:|--:|--:|--:|
| 37 | 4 | 85 | 35 | 47 | 3 |
| 617 | 16 | 325 | 115 | 207 | 3 |
| 3017 | 16 | 371 | 153 | 208 | 10 |

**prefill はほぼ効かず、生成トークン数がそのままレイテンシになる。**

そこで判定の出力を `{"mode":"navigate"}` から `{"m":"n"}` へ短縮したところ、
600ms → 約 500ms になった (精度は変わらず navigate 100%)。
残りは 1 リクエストあたりの固定費で、これ以上は縮まない。

→ **`--parallel 2` は不要だった。** 誤った仮説のまま別リポジトリの設定を
変更しなくてよかった。Gate のコストは「LLM 呼び出しが 1 回増える」ことそのもので、
このモデル・この構成では約 500ms が下限。

### 4. 画面遷移が権限を迂回していないかを検証していなかった

navigate で終わると Tool 結果が無いので、それまでの権限検証は素通りしていた。
評価ハーネスが**遷移先の画面を実際に開いて**表示データを検証するようにした。
その過程で BFF の実バグを 1 つ発見した (顧客サービスの 403 を 502 へ潰していた)。

## 150 件でのモデル階段 (2026-08-31)

| モデル | 総合 | 必須Tool | step超過なし | 平均step |
|---|--:|--:|--:|--:|
| Gemma 4 12B | **99%** | 99% | **100%** | 2.4 |
| Qwen3.6-35B-A3B IQ4_XS | 83% | 97% | 87% | 3.3 |
| Qwen3.5 4B | 82% | 93% | 93% | 3.1 |
| Qwen3.6-35B-A3B IQ3_S | 78% | 99% | 79% | 3.8 |
| Qwen3.5 9B | 77% | 97% | 82% | 3.8 |

40 件では 100 / 100 / 98 / 98 / 92% でほぼ差が無かったものが、150 件で 16〜22 ポイント開いた。

**分かれたのは Tool 選定ではなく「いつ止めるか」だった。**
必須Tool の到達率はどのモデルも 93〜99% で並ぶ。差が出たのは step超過なしの列で、
Gemma だけが 100%、他は 79〜93%。

40 件のセットにはステップ上限も exploration カテゴリも無かったため、
**この軸を 1 つも測っていなかった**。評価セットに無い性質は、
どれだけ回数を重ねても見えない。

→ D13 (モデルを Gemma 4 12B に確定) は、より強い根拠で裏付けられた。

## §13 WRITE Command Proposal (2026-08-31)

READ-only だった基盤に更新操作を足した。ただし **LLM は実行しない**。

```
User → LLM → 提案 (未実行) → 画面で人間が確認 → BFF → サービスの更新 API
```

### 境界

| 層 | 責務 |
|---|---|
| `catalog/commands.json` | 提案してよい操作と引数。ここに無いものは文法で生成できない |
| LLM | 提案を1つ作るだけ。実行しない。可否も判断しない |
| Executor | 更新 API の存在を知らない。READ Tool しか持たない |
| 画面 | 人間が内容を確認して承認する |
| BFF | 承認された内容をカタログに対して検証し直し、権限を確認して転送 |
| サービス | **業務ルールを判断する**。キャンセル可能な状態か、など |

実測で確かめた境界:

| 操作 | 結果 |
|---|---|
| O-1002 (PLACED) をキャンセル | 200 |
| O-1001 (SHIPPED) をキャンセル | **409** 「SHIPPED のためキャンセルできません」 |
| 既にキャンセル済みを再度 | **409** |
| support ロールが注文を更新 | **403** 「参照専用」 |
| EAST 営業が WEST の注文を | **404** (存在を秘匿) |
| sales ロールが在庫を更新 | **403** |
| 定義外の引数 `force` を混ぜる | 黙って落とされる |

**可否の判断はすべてサービス側にある。** LLM も BFF もこれを代行しない。
書き込み権限は参照権限と別に定義した (`authctx.writeMatrix`)。
support は全件参照できるが 1 つも更新できない。

### モード判定を 3 値へ広げても劣化しなかった

Intent Gate を navigate / tool の 2 択から navigate / tool / write の 3 択にした。
懸念していた既存カテゴリの劣化は起きなかった。

| カテゴリ | 2 値のとき | 3 値のとき |
|---|--:|--:|
| navigate | 100% | 100% |
| single_tool | 100% | 100% |
| exploration | 100% | 100% |
| ambiguity | 96% | 96% |

### また同じ失敗をした — そして同じ構造で直した

write モードでも「Tool を実行した後に終端の行動へ戻れない」が再現した
(対象を特定した後、提案せずに情報収集を続ける)。

navigate のときと同じ手を打った。**Tool が1回成功したら、Tool の選択肢を
スキーマから外す**。これで 80% → 90% になった。

| 対策 | write 正答 |
|---|--:|
| プロンプトのみ | 55% |
| 「引数が揃っていれば Tool を使わず提案」を明示 | 80% |
| + Tool 実行後は Tool をスキーマから外す | **95%** |

プロンプトで 25 ポイント、構造でさらに 15 ポイント。
**このプロジェクトで 3 回続けて、終端の行動へ戻す制御はプロンプトでは足りなかった。**

### 170 件の最終成績 (Gemma 4 12B)

| カテゴリ | n | 総合 |
|---|--:|--:|
| navigate | 25 | 100% |
| single_tool | 20 | 100% |
| multi_hop | 18 | 100% |
| cross_service | 25 | 100% |
| permission | 22 | 100% |
| exploration | 15 | 100% |
| write | 20 | 95% |
| ambiguity | 25 | 96% |
| **合計** | **170** | **98.8%** |

| 完了経路 | 件数 | 平均 ms | 平均 step |
|---|--:|--:|--:|
| 遷移 | 33 | 2288 | 1.0 |
| 提案 | 11 | 3655 | 1.5 |
| Tool | 126 | 4582 | 2.8 |

## 監査と Observability (2026-08-31)

更新を実行しても、残るのは stderr のテキストログ 1 行だけだった。

```
msg=execute user=u_admin command=customer.updateContact status=200
```

**何を何に変えたのかが記録されていない。** 引数も、どの提案に対する承認だったのかも
残らない。LLM が業務データの変更を提案する仕組みを作った以上、これは機能不足ではなく
欠陥なので塞いだ。

### 置き場所

`audit` schema を新設し、**BFF が所有する**。記録するのは「システムが何をしたか」で
あって業務データではなく、リクエストの入口を持つのが BFF だから。
マイクロサービスはこの schema を参照しない。

| テーブル | 内容 |
|---|---|
| `audit.traces` | 1 リクエスト = 1 行。判定 (intent)、結果、レイテンシ、トークン |
| `audit.trace_steps` | Loop の 1 ステップ = 1 行。Tool と引数と Projection 済み結果 |
| `audit.command_executions` | 更新の実行 1 回 = 1 行。**拒否された試行も残す** |

元案 §21 の Observability が求めていたもの
(User Request → Selected Tools → Tool Arguments → API Response → Final Response) は、
**すでに `Trace` 構造体が全部持っていた**。捨てていただけだった。

### 拒否も記録する

監査の本体は「誰が何をやろうとしたか」なので、成功だけを残しても意味がない。

| 記録された試行 | status |
|---|--:|
| admin が PLACED の注文をキャンセル | 200 |
| admin が SHIPPED の注文をキャンセル | 409 |
| support が注文を更新 | 403 |

引数と拒否理由も一緒に残る。

### 失敗しても止めない、ただし黙らない

- 監査の書き込みに失敗してもユーザーの操作は止めない (best-effort)。ただしログに残す
- 監査を無効にして起動すると **WARN を出す**。静かに無効化しない
- **不正な DSN を渡すと起動時に落ちる。** 設定ミスを握り潰して「記録しているつもり」を作らない
- 記録はリクエストの context を使わない (応答済みで cancel されているため)

### 閲覧は admin のみ

誰が監査を見られるかは業務データの権限とは別の判断になるので、いまは admin だけに開いた。
自分のトレースだけ見せる、監査ロールを作るといった設計は運用要件次第。

### 副次効果

トレースが溜まると**ゴールデンセットの材料になる**。現状 170 件はすべて手書きで、
実際にユーザーが何を尋ねるかは反映されていない。ここが今後の品質改善のボトルネックだった。

なお記録されるのは **BFF 経由の実利用だけ**で、評価ハーネス (Orchestrator を直接呼ぶ) は
記録しない。テストのトレースが実利用の記録に混ざらないようにするため。
