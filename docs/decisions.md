## 元案からの主な変更

### C1. Response Projection を設計の中心に置く

元案には項目自体がなかったが、実 API の JSON をそのまま context に戻すと小型モデルは破綻する。
Tool 定義ごとに「LLM へ返すフィールドの whitelist」「最大件数」「ネスト展開の深さ」を必須項目とする。

### C2. context 削減は「履歴の後処理」ではなく「Tool Result 追加時点の Projection」で行う

`--cache-reuse 256` が有効なため、prompt prefix をバイト単位で安定させる必要がある。
途中で履歴を要約圧縮すると prefix が壊れてフル再 prefill になり、レイテンシが跳ねる。

Orchestrator が守る制約:

- system prompt と Tool 定義の順序を固定する（map の iteration 順で並べない）
- prefix に現在時刻・ランダム ID・リクエスト ID を入れない
- 履歴は append のみ

### C3. モデル階段は単調ではない

`Qwen3.6-35B-A3B` は active 3B の MoE。総パラメータは 35B だが 1 トークンあたりに通る重みは 3B 相当。
Tool 選定と引数抽出は精度タスクなので、dense `Qwen3-14B Q4_K_M` (active 14B / 4.8bpw) が
`35B-A3B IQ3_S` (active 3B / 3.4bpw) を上回る可能性がある。上限を決め打ちせず測定する。

### C4. ルーティング段数を測定対象に格上げ

PoC 規模（5 サービス / 24 API）では Stage 1 の追加往復がレイテンシを支配しうる。
2 段階を前提とせず、1 段階と同一条件で比較する。

## 保留

- **ceiling の妥当性**: ローカル最大構成で失敗した場合、「アーキが悪い」のか「まだモデルが小さい」のか
  切り分けられない。LLM クライアントを OpenAI 互換インターフェース 1 枚に閉じ込め、切り分けが
  必要になった時点でホスト型モデルへ向けられる状態だけ確保しておく（使うかは後で判断）。

## スケール検証で決着した論点 (2026-08-31, 24〜504 Tool)

元案 §7〜§9 の 2 段階ルーティング (Stage 1 Service Router → Stage 2 Tool Selector) は
**削除してよい**。24〜504 Tool の全域で、`loose` + Executor 検証の 1 段階が
精度・レイテンシとも 2 段階以上だった。

前提だった「全 API 定義を context に入れられない」は prefix cache のある環境では成立しない。
Tool 定義は約 48 tok/Tool で線形に増えるが (504 Tool = 24,363 tok)、
system prompt が固定である限り prefill はキャッシュが吸収する。
**`loose` なら 124 → 504 Tool でレイテンシが +7% しか増えない。**

代わりに効いてくるのは 2 つ。

1. **`anyOf` 分岐の GBNF 文法コスト** — 124 Tool で +30%、504 Tool で **+111〜123%**。
   Executor 側の検証 (`invalidEnums` / `sanitizeArgs`) へ逃がせる。
2. **モデルの限界** — Gemma 4 12B は 504 Tool でも 100%、
   Qwen3.6-35B-A3B は 304 Tool 付近から崩れて 504 Tool で 90%。
   **「何 Tool まで大丈夫か」はアーキテクチャではなくモデルの性質だった。**

詳細は [scale-report.md](scale-report.md)。

## §14 UI State 生成で分かったこと (2026-08-31)

Tool Loop の分岐に `navigate` を 1 つ加えるだけで実装できた。LLM 呼び出しは増えない。
遷移先とフィルタは `catalog/routes.json` に定義したものしか書けないよう `anyOf` で固定する。
Tool Registry と同じ構造を UI ルートへ適用した形。

**速い。** 画面遷移で済む要求は Tool を 1 回も実行しないので、
1.3〜2.0 秒で完了する (Tool 経路は 4〜8 秒)。

### モードの切り替えはプロンプトでは制御しきれなかった

- 画面セクションを Tool セクションの**後ろ**に置くと、`navigate` を一度も選ばなかった (3/3)。
  前に出して判断例を添えたら選ぶようになった。**24 個の Tool 定義に埋もれていた。**
- 「Tool で ID を解決してから navigate する」は、指示を補強しても最後まで再現しなかった。
  **12B モデルはループの途中でモードを切り替えられない。**

### 解決策は「モデルに ID を解決させない」ことだった

画面のフィルタ語彙をユーザーの言葉に合わせる。`/orders` に `customer_name` を足し、
氏名から顧客 ID への解決は BFF の Aggregation で行う。
これで多段の navigate が不要になり、1 ステップで遷移できるようになった。

**LLM に難しい手順を踏ませるより、踏まなくて済むインターフェースを与える方が確実。**

## ゴールデンセット拡充と Intent Gate (2026-08-31)

40 件 → **150 件**へ拡充した (navigate 25 / exploration 15 を新設、既存 5 カテゴリも増量)。
拡充して初めて見えたことが 2 つある。

### 1. §14 は navigate を過剰にも過少にも誤る

40 件のセットでは navigate ケースが 1 つも無く、まったく測れていなかった。
150 件で測ると、プロンプトの書き方次第で両方向に振れた。

| プロンプト | 症状 |
|---|---|
| 画面セクションを Tool の後ろ | navigate を一度も選ばない |
| 画面セクションを前 + 判断例 | 画面が無い領域 (商品・配送業者) でも遷移する |
| 「画面が無いものは Tool」を明示 | 今度は遷移すべき場面で遷移しない (navigate 72%) |

**3 回測って 76% / 76% / 76%。ばらつきではなく一貫した失敗だった。**
プロンプトの往復では収束しない。

### 2. 構造で解いた — Intent Gate

Loop に入る前に「画面を開くだけで満たせるか」を **2 択で 1 回だけ判定**し、
以降の選択肢をその側だけに絞る (`Options.IntentGate`)。
navigate 側なら Tool を一切見せず、tool 側なら画面を見せない。

**27 分岐の中からモードを選ばせるのをやめ、2 択にした。**

| 構成 | navigate 正答 | 全 150 件 |
|---|--:|--:|
| Intent Gate なし | 72% | — |
| Intent Gate あり | **100%** | **99.3%** |

### 3. Gate のコストは 1 リクエスト分の固定費だった

当初「2 つの system prompt が KV キャッシュを奪い合っているのが主因」と書いたが、
**これは誤りだった**。測り直した結果を残しておく。

まず機序の確認。長短 2 つのプロンプトを連続実行と交互実行で比べると:

| 条件 | cache 率 | prefill 合計 |
|---|--:|--:|
| A のみ連続 (6 回) | 99.1% | 678ms |
| B のみ連続 (6 回) | 99.9% | 901ms |
| A/B 交互 (6 回) | 94.0% | 1169ms |

奪い合いは実在するが、コストは 1 ペアあたり約 127ms にすぎない。

次に実際の intent 呼び出しを直接測ると、**連続でも交互でも一貫して約 600ms** だった。
つまりキャッシュ状態と無関係。内訳は 18 トークンの生成で、
制約デコード下では 1 トークンあたり約 33ms (非制約時は約 13ms) かかっていた。

| prompt tok | 生成 tok | wall ms | prefill | 生成 | その他 |
|--:|--:|--:|--:|--:|--:|
| 37 | 4 | 85 | 35 | 47 | 3 |
| 617 | 16 | 325 | 115 | 207 | 3 |
| 3017 | 16 | 371 | 153 | 208 | 10 |

**prefill はほぼ効かず、生成トークン数がそのままレイテンシになる。**

そこで判定の出力を `{"mode":"navigate"}` から `{"m":"n"}` へ短縮したところ、
600ms → 約 500ms になった (精度は変わらず navigate 100%)。
残りは 1 リクエストあたりの固定費で、これ以上は縮まない。

→ **`--parallel 2` は不要だった。** 誤った仮説のまま別リポジトリの設定を
変更しなくてよかった。Gate のコストは「LLM 呼び出しが 1 回増える」ことそのもので、
このモデル・この構成では約 500ms が下限。

### 4. 画面遷移が権限を迂回していないかを検証していなかった

navigate で終わると Tool 結果が無いので、それまでの権限検証は素通りしていた。
評価ハーネスが**遷移先の画面を実際に開いて**表示データを検証するようにした。
その過程で BFF の実バグを 1 つ発見した (顧客サービスの 403 を 502 へ潰していた)。

## 150 件でのモデル階段 (2026-08-31)

| モデル | 総合 | 必須Tool | step超過なし | 平均step |
|---|--:|--:|--:|--:|
| Gemma 4 12B | **99%** | 99% | **100%** | 2.4 |
| Qwen3.6-35B-A3B IQ4_XS | 83% | 97% | 87% | 3.3 |
| Qwen3.5 4B | 82% | 93% | 93% | 3.1 |
| Qwen3.6-35B-A3B IQ3_S | 78% | 99% | 79% | 3.8 |
| Qwen3.5 9B | 77% | 97% | 82% | 3.8 |

40 件では 100 / 100 / 98 / 98 / 92% でほぼ差が無かったものが、150 件で 16〜22 ポイント開いた。

**分かれたのは Tool 選定ではなく「いつ止めるか」だった。**
必須Tool の到達率はどのモデルも 93〜99% で並ぶ。差が出たのは step超過なしの列で、
Gemma だけが 100%、他は 79〜93%。

40 件のセットにはステップ上限も exploration カテゴリも無かったため、
**この軸を 1 つも測っていなかった**。評価セットに無い性質は、
どれだけ回数を重ねても見えない。

→ D13 (モデルを Gemma 4 12B に確定) は、より強い根拠で裏付けられた。

## §13 WRITE Command Proposal (2026-08-31)

READ-only だった基盤に更新操作を足した。ただし **LLM は実行しない**。

```
User → LLM → 提案 (未実行) → 画面で人間が確認 → BFF → サービスの更新 API
```

### 境界

| 層 | 責務 |
|---|---|
| `catalog/commands.json` | 提案してよい操作と引数。ここに無いものは文法で生成できない |
| LLM | 提案を1つ作るだけ。実行しない。可否も判断しない |
| Executor | 更新 API の存在を知らない。READ Tool しか持たない |
| 画面 | 人間が内容を確認して承認する |
| BFF | 承認された内容をカタログに対して検証し直し、権限を確認して転送 |
| サービス | **業務ルールを判断する**。キャンセル可能な状態か、など |

実測で確かめた境界:

| 操作 | 結果 |
|---|---|
| O-1002 (PLACED) をキャンセル | 200 |
| O-1001 (SHIPPED) をキャンセル | **409** 「SHIPPED のためキャンセルできません」 |
| 既にキャンセル済みを再度 | **409** |
| support ロールが注文を更新 | **403** 「参照専用」 |
| EAST 営業が WEST の注文を | **404** (存在を秘匿) |
| sales ロールが在庫を更新 | **403** |
| 定義外の引数 `force` を混ぜる | 黙って落とされる |

**可否の判断はすべてサービス側にある。** LLM も BFF もこれを代行しない。
書き込み権限は参照権限と別に定義した (`authctx.writeMatrix`)。
support は全件参照できるが 1 つも更新できない。

### モード判定を 3 値へ広げても劣化しなかった

Intent Gate を navigate / tool の 2 択から navigate / tool / write の 3 択にした。
懸念していた既存カテゴリの劣化は起きなかった。

| カテゴリ | 2 値のとき | 3 値のとき |
|---|--:|--:|
| navigate | 100% | 100% |
| single_tool | 100% | 100% |
| exploration | 100% | 100% |
| ambiguity | 96% | 96% |

### また同じ失敗をした — そして同じ構造で直した

write モードでも「Tool を実行した後に終端の行動へ戻れない」が再現した
(対象を特定した後、提案せずに情報収集を続ける)。

navigate のときと同じ手を打った。**Tool が1回成功したら、Tool の選択肢を
スキーマから外す**。これで 80% → 90% になった。

| 対策 | write 正答 |
|---|--:|
| プロンプトのみ | 55% |
| 「引数が揃っていれば Tool を使わず提案」を明示 | 80% |
| + Tool 実行後は Tool をスキーマから外す | **95%** |

プロンプトで 25 ポイント、構造でさらに 15 ポイント。
**このプロジェクトで 3 回続けて、終端の行動へ戻す制御はプロンプトでは足りなかった。**

### 170 件の最終成績 (Gemma 4 12B)

| カテゴリ | n | 総合 |
|---|--:|--:|
| navigate | 25 | 100% |
| single_tool | 20 | 100% |
| multi_hop | 18 | 100% |
| cross_service | 25 | 100% |
| permission | 22 | 100% |
| exploration | 15 | 100% |
| write | 20 | 95% |
| ambiguity | 25 | 96% |
| **合計** | **170** | **98.8%** |

| 完了経路 | 件数 | 平均 ms | 平均 step |
|---|--:|--:|--:|
| 遷移 | 33 | 2288 | 1.0 |
| 提案 | 11 | 3655 | 1.5 |
| Tool | 126 | 4582 | 2.8 |

## 監査と Observability (2026-08-31)

更新を実行しても、残るのは stderr のテキストログ 1 行だけだった。

```
msg=execute user=u_admin command=customer.updateContact status=200
```

**何を何に変えたのかが記録されていない。** 引数も、どの提案に対する承認だったのかも
残らない。LLM が業務データの変更を提案する仕組みを作った以上、これは機能不足ではなく
欠陥なので塞いだ。

### 置き場所

`audit` schema を新設し、**BFF が所有する**。記録するのは「システムが何をしたか」で
あって業務データではなく、リクエストの入口を持つのが BFF だから。
マイクロサービスはこの schema を参照しない。

| テーブル | 内容 |
|---|---|
| `audit.traces` | 1 リクエスト = 1 行。判定 (intent)、結果、レイテンシ、トークン |
| `audit.trace_steps` | Loop の 1 ステップ = 1 行。Tool と引数と Projection 済み結果 |
| `audit.command_executions` | 更新の実行 1 回 = 1 行。**拒否された試行も残す** |

元案 §21 の Observability が求めていたもの
(User Request → Selected Tools → Tool Arguments → API Response → Final Response) は、
**すでに `Trace` 構造体が全部持っていた**。捨てていただけだった。

### 拒否も記録する

監査の本体は「誰が何をやろうとしたか」なので、成功だけを残しても意味がない。

| 記録された試行 | status |
|---|--:|
| admin が PLACED の注文をキャンセル | 200 |
| admin が SHIPPED の注文をキャンセル | 409 |
| support が注文を更新 | 403 |

引数と拒否理由も一緒に残る。

### 失敗しても止めない、ただし黙らない

- 監査の書き込みに失敗してもユーザーの操作は止めない (best-effort)。ただしログに残す
- 監査を無効にして起動すると **WARN を出す**。静かに無効化しない
- **不正な DSN を渡すと起動時に落ちる。** 設定ミスを握り潰して「記録しているつもり」を作らない
- 記録はリクエストの context を使わない (応答済みで cancel されているため)

### 閲覧は admin のみ

誰が監査を見られるかは業務データの権限とは別の判断になるので、いまは admin だけに開いた。
自分のトレースだけ見せる、監査ロールを作るといった設計は運用要件次第。

### 副次効果

トレースが溜まると**ゴールデンセットの材料になる**。現状 170 件はすべて手書きで、
実際にユーザーが何を尋ねるかは反映されていない。ここが今後の品質改善のボトルネックだった。

なお記録されるのは **BFF 経由の実利用だけ**で、評価ハーネス (Orchestrator を直接呼ぶ) は
記録しない。テストのトレースが実利用の記録に混ざらないようにするため。

## コンテナ構成 (2026-08-31)

元案 §3 の構成をそのまま立てた。

```
Browser → Nginx (:8081) → BFF → Microservices ×5 → PostgreSQL
                                  ↓
                         host の llama-swap (:11435)
```

ホストへ公開するのは **Nginx だけ**。DB も BFF も各サービスも内部ネットワークに閉じる。

### 詰まった点

**Postgres 18 でデータの置き場所が変わっていた。** `/var/lib/postgresql/data` に
ボリュームを当てると `unused mount` として起動を拒否される。`/var/lib/postgresql`
にマウントする必要がある。

**`go.work` はイメージに入れない。** ワークスペースを持ち込むと評価ハーネス (eval) の
モジュールまで必要になる。各モジュールの `replace` で解決させれば、
実行に要らないものを含めずに済む。

**Nginx の既定はバッファする。** そのままだと Tool Loop の進捗が最後まで届かず、
数秒〜数十秒のあいだ画面が固まったように見える。`proxy_buffering off` が必須。
実測では step が 1 秒ごとに届いている (15:21:15 / :16 / :18 / :19)。

### base_url はデプロイ構成であって Tool 定義ではない

カタログの `base_url` は `127.0.0.1:910x` を指しているが、compose 内では
サービス名で解決する必要がある。環境変数 `NLOPS_BASE_<SERVICE>` で上書きできるようにした。
Tool の定義 (名前・説明・引数) と接続先は別物なので、後者だけを差し替えられる形にしている。

### LLM はホストのものを共有する

llama-swap をコンテナ内に持ち込むと VRAM を二重に消費する。16GB では成立しないので、
`host.docker.internal` でホストの `:11435` へ出る。
このため **compose だけでは完結せず、ホスト側に llama-swap が必要**。

### TLS は「証明書があれば有効」にした

構成を 2 つ用意して切り替えるのではなく、起動スクリプトが
`/etc/nginx/certs/` を見て HTTPS の server ブロックを配置する。
証明書が無ければ HTTP のみで上がる。

tailnet で使うなら `tailscale cert` で本物の証明書が取れるので、
自己署名 (`make cert`) は手元確認用の位置づけ。

### 秘密情報は Docker secrets にした

最初 `.env` へ移して「平文で残るのは次の段階」と書いたが、それは解消したことに
ならない。環境変数に置いた秘密は次の経路で読める。

- `docker inspect` の `Config.Env`
- `/proc/<pid>/environ`
- 子プロセスへの自動的な引き継ぎ

Docker secrets ならファイルとして `/run/secrets` にマウントされ、上のどれにも出ない。

| 消費者 | 渡し方 |
|---|---|
| PostgreSQL | `POSTGRES_PASSWORD_FILE=/run/secrets/db_password` |
| Go の各サービス / BFF | `NLOPS_DSN_FILE=/run/secrets/db_dsn` |

同じパスワードから `make secrets` が両方を生成するのでずれない。
`deploy/secrets/` は追跡しない。実測で `docker inspect` に秘密が出ないことを確認した。

**ファイルの権限で 1 つ踏んだ。** compose の file 型 secret はホストのファイルを
bind mount するので、ホスト側の所有者と権限がそのまま効く。600 のままだと
非 root (uid 65532) のコンテナから読めない。ファイルを 644 にし、
**保護はディレクトリの 700 が担う**形にした (他ユーザーは辿れない)。

このとき DSN が空文字になり「unix socket に繋がらない」という無関係なエラーが出て
原因が分かりにくかったので、`pkg/dbconf` がファイルを読めなかった理由を
stderr へ出すようにした。

### PostgreSQL のパスワードは初回起動時にしか適用されない

ボリュームが残ったままパスワードを変えると認証に失敗する (`make reset` が必要)。
このとき BFF は起動時に落ちて理由をログへ出したので原因はすぐ分かった。
「設定ミスを握り潰さない」方針が効いた形。

### 手元固有の設定はリポジトリに入れない

ローカル開発の `make db` が別プロジェクトの PostgreSQL コンテナ名と認証情報を
直書きしていた。変数化し、手元の値は `local.mk` (追跡しない) へ移した。

### バンドル分割の効果は限定的だった

画面ごとに `lazy` で分割した。最大チャンクは 518kB → 244kB になり警告も消えたが、
**初回ロードは gzip 161kB → 152kB の 6% 改善にとどまった**。
MUI が全画面で共有されるので、分割しても初回に必要な量がほとんど減らない。

これ以上を狙うなら MUI の使用範囲を絞る必要があり、割に合わない。
社内向けの業務画面としては 152kB は許容範囲と判断した。

## データ規模の検証 (2026-09-01)

### きっかけ — 170 ケースまで詰めておいて、データが 11 件だった

Tool 数は 504 まで検証したのに、**中身のデータ量を一度も疑っていなかった**。
最大のテーブルで注文 11 件。この状態では:

- Projection の `max_items` (20) は**一度も発火していない**
- 全サービスの SQL に `LIMIT` が 1 つも無い (`grep -c LIMIT services/cmd/*/main.go` → 全て 0)
- 「同姓の顧客が複数いる」状況が作れないので、曖昧性の判断を測れない

result.md に 3 回「大きな結果集合で測り直す必要がある」と書きながら、
測れるデータを用意していなかった。

顧客 5,006 / 注文 50,011 / 明細 99,906 / 出荷 48,019 / 請求 49,008 / 商品 506 を投入した
(`services/schema/bulk/010_bulk_seed.sql`, `make db-bulk`)。

### 追加データはゴールデンセットを壊さないように作る

170 ケースは `C001` `O-1001` といった具体的な ID と「田中太郎さん」という
具体的な氏名に依存している。バルクは:

- ID を既存より後ろに (`C10001-`, `O-50001-`)、日付を既存より古くする
  → 一覧は新しい順なので既存データが先頭に残る
- 姓は意図的に重複させる (「田中」で 252 件) → 曖昧性を測れるようにする

**ここで 1 つ外した。** 名も既存と同じ配列から採ったため、
`田中太郎` `佐藤花子` 等に 13〜14 人の同姓同名が生えた。
氏名で 1 件に特定する前提のケースが成立しなくなり、write が 90% へ落ちた。
名の配列から種顧客 6 人の名を外して解決した。
**バルク内には同姓同名が 12〜13 人ずつ残してある** (曖昧性の検証にはこれが要る)。

### 露出した問題 1: サービスが全件返していた

`GET /api/orders` が **6,975,907 バイト / 50,011 行 / 1.03 秒**。
LLM に 20 行見せるために 7MB 転送していた。

`svc.ListPage` を入れて 1 ページ (既定 100 / 上限 1000) に切った。
**42,337 バイト / 0.013 秒**。

ここで新しいバグを作りかける形になった。単純に `LIMIT` すると
`count` がページサイズになり、**「未発送の注文は何件ありますか」に
LLM が「100 件」と答える**。`count` には該当総件数を入れ、
実際に返した行数は `returned` / `has_more` で伝える。
`executor.project()` もサービスの `count` を保持するようにした。

実測で確認: 「未発送の注文は何件ありますか」→ 「PLACED 514 件、CONFIRMED 476 件、
合計 990 件」。ページサイズではなく総件数を答えている。

### 露出した問題 2: reason にモデルが全行を書き出して max_tokens に達した

170 件中 3 件が `finish_reason: length` で JSON が閉じないまま落ちた。
生成内容を見ると:

```
{"next":"finish","reason":"配送に失敗した出荷…合計144件あり、そのうちの最初の20件…
1. 注文ID: O-1008, 出荷ID: S-3005, 配送業…
```

**`reason` の中に結果を全部書き出していた。** 結果が 11 件のときは起きなかった。

プロンプトで「短く書いて」と頼むのではなく、スキーマに `maxLength: 120` を入れた。
llama.cpp の JSON Schema → GBNF 変換は `maxLength` を文法に落とすので、
**長く書くこと自体ができなくなる**。512 tok → 99 tok。

この PoC で繰り返し出てきた「プロンプトで頼まず構造で禁じる」がまた効いた。

### 露出した問題 3: 候補が 250 件ある中の 1 件で更新を提案していた

「山田さんの電話番号を変更して」→ `customer.search(name=山田)` が 250 件 →
モデルが**先頭の C10011 山田太郎を選んで更新提案**を出した。

読み取りなら誤りは画面で気づける。更新は違う。
承認画面には 1 件しか出ないので、**他に 249 件候補があったという事実が
承認者から消える**。人間が承認した時点で確定してしまう。

`UnresolvedIDs` (捏造 ID の差し戻し) と同じ位置に曖昧 ID ガードを足した。
候補が 2 件以上あった一覧に出てきた ID には印を付け、更新提案の引数に
使われたら差し戻す。1 件に絞り込めた検索の結果は印を外す
(「山田」250 件 → 「山田太郎」1 件 なら通す)。
利用者が自分で書いた ID (「C005 のメールを更新して」) は最初から対象外。

導入後: 「山田さんの…」→ 提案を止め、
「複数存在するため更新対象を特定できません。顧客IDやフルネームを教えてください」
と利用者に返すようになった。

### 露出した問題 4: BFF が一覧同士をメモリで突き合わせていた

`GET /api/orders?customer_name=…` は、顧客一覧と注文一覧をそれぞれ 1 ページ取って
BFF のメモリで突き合わせていた。データが 11 件のうちは動く。

5 万件では「新しい順 100 件の注文」と「顧客の先頭 100 件」が重ならないので、
**実在する注文に対して 0 件を返す**。

氏名 → 顧客 ID 集合に解決したうえで、その集合を注文サービスへ渡す
(`customer_ids`, `svc.W.In`) 形に直した。表示用の顧客名も、
返ってきた注文の顧客だけを引く。

絞り込めない場合 (「田中」= 252 件) は、一部だけ返して「これが全部です」と
見せるより、**絞り込めなかったと伝える**ほうを選んだ。

### 画面にも総件数を出す

サービスが 1 ページしか返さなくなったので、画面が 100 行を並べたまま黙っていると
利用者は「これで全部だ」と読む。「50,011 件中 1–25 件」を明示するようにした
(この表示は後にページ送りの `TablePagination` が兼ねている)。

### 結果: 171 ケースで 99.4%。データ量で精度は落ちなかった

| 段階 | 総合 | 失敗 |
|---|--:|---|
| データ 11 件 (170 件) | 98.8% | D22 + write 1 + ambiguity 1 |
| バルク投入直後 (170 件) | 96.0% | max_tokens 3 / 曖昧提案 1 / D22 / W06 |
| 上記 4 つの修正後 (171 件) | **99.4%** | D22 のみ |

**データを 5,000 倍にしても精度は落ちなかった。**
落ちたのは、データが小さいうちは存在しなかった 4 つの欠陥が露出したからで、
いずれも構造で塞げた。

### Projection の効果 — ようやく測れた。そして主張は半分外れた

result.md に 3 回「大きな結果集合で測り直す」と書いていた宿題。

| | 総合 | prompt tok | cache 率 | 平均 ms | LLM 投入 B |
|---|--:|--:|--:|--:|--:|
| Projection ON | **99%** (170/171) | 5,269 | 85% | 4,154 | 551 |
| Projection OFF | **99%** (169/171) | 10,390 | 58% | 5,020 | 8,371 |

**コスト面は明確**: prompt トークン +97%、キャッシュ率 85% → 58%、レイテンシ +21%。

**精度面は依然として差が出なかった。** 1 件差は有意ではない。
当初の「Projection が無いと小型モデルが破綻する」という主張は、
**5 万件のデータでも裏付けられなかった。**

理由ははっきりしている。**サービス側のページングが先に効いているから**だ。
1 ページ 100 行に切られた後なら、Projection を切っても 8KB にしかならない。
モデルはそれを読める。

破綻するのはページングが無い場合で、そのとき生レスポンスは 6.98MB =
約 170 万トークンあり、32k の context に**入らない**。
つまりこれは「精度が落ちる」ではなく「動かない」であり、
Projection ではなく**ページングが防いでいる**。

→ 順序を正しく言うと: **一次防御はサービス側のページング。
Projection はその上に乗るコスト最適化**であって、精度の保険ではない。
C2「Response Projection を必須にした」の判断自体は変えないが、
理由を「context に入らなくなるから」から
「トークンとキャッシュのコストが 2 倍になるから」へ書き換える。

### ページ送り — LLM には見せない

画面には `TablePagination` を入れ、`limit` / `offset` を URL に置いた
(フィルタと同じ場所。URL を共有すれば同じ画面が再現できる)。

**Tool の引数には出さない。** `offset` を LLM に見せると、
「未払いの請求書を全部見せて」に対して 108 ページ分の往復を始める。
LLM が受け取るのは `count` / `items` / `shown` / `truncated` の 4 つだけで、
`offset` `limit` `returned` `has_more` は Projection が落とす (実測で確認)。
足りなければページを送るのではなく**絞り込ませる**。これは
「LLM に権限を持たせない」「URL を持たせない」と同じ考え方で、
**やらせたくないことは指示ではなく到達不能にする**。

`has_more` の定義で 1 つ踏みかけた。`count > returned` にすると
2 ページ目以降で常に true になり、最終ページで「次がある」と嘘をつく。
`offset + returned < count` が正しい。ユニットテストで固定した。

**offset は深いページほど遅い。** 実測 (注文 50,011 件 / 100 件ずつ):

| offset | 応答時間 |
|--:|--:|
| 0 | 14ms |
| 5,000 | 20ms |
| 49,900 | 46ms |

読み飛ばすコストなので線形に増える。この規模なら許容だが、
100 万件では keyset (cursor) 方式へ変える必要がある。
上限 `MaxOffset = 100,000` を置いて、1 リクエストで DB を舐めさせないようにした。

### 並べ替え — ページ送りではなく順序で解く (2026-09-02)

**きっかけの問い**: 「一番古い田中のレコードが欲しい。`order_by` が無い場合、
LLM はページネーションの最後を取ってくる回り道で解決できるか。」

まず実測した (データは注文 50,011 件、一覧の既定は新しい順)。

| 質問 | 回答 | 正解 |
|---|---|---|
| 田中**太郎**さんの一番古い注文 | O-1001 / 2026-08-20 | ○ (3 件しかなく 1 ページに収まる) |
| **田中**さんの一番古い注文 | 「**田中太郎**さんの…O-1001 / 2026-08-20」 | ✗ O-50019 / 2024-01-20 (田中陽菜) |
| 一番古い注文 | O-89479 / **2026-07-28** | ✗ O-50940 / **2024-01-01** |

**2 年 7 か月ずれた。** しかも断定形で、見えている 20 件が全体でないことに触れていない。

分かったことは 3 つ:

1. **ページ送りの回り道は取れない。** `offset` は意図的に LLM へ出していない
   (出すと 500 ページ舐めに行くため)。設計どおりの結果。
2. **別の回り道は存在し、モデルはそれを使える。** `order.search` には
   `ordered_from` / `ordered_to` がある。「2024年1月の注文を見せて」と聞けば
   正しく使って 1,673 件を返す。**道具はあった。**
3. **しかし自分からは使わない。** `count: 50011` / `truncated: true` / `shown: 20`
   を見ているのに、「50,011 件のうち 20 件しか見えていないのだから絞り込まねば」
   とは考えない。

3 番目は誤 Tool 検証 ([recovery-report.md](recovery-report.md)) の結論と同じだった。
**モデルは「質問が要求するもの」ではなく「答えらしい形をしているもの」から答える。**
並び順が要求に合っているかは見ていない。

#### offset ではなく sort を出した

##### 最初の理由づけは間違っていた

当初「`offset` を与えれば 2,500 ページ歩かせることになる」と書いた。**これは誤り。**
一覧は総件数 `count` を返すので、モデルは `offset = count - limit` を計算して
**最後のページへ 1 回で飛べる**。歩く必要はない。

指摘を受けて、`sort` を外して `offset` / `limit` だけを出したカタログで実測した。

| 質問 | モデルの動き | 結果 |
|---|---|---|
| 一番古い注文 | step2 で `offset: 50000` | **O-50940 / 2024-01-01** ○ |
| 一番高額な注文 | step2 で `offset: 20` | 228,000 だが**見えた 40 件の中の最大**。偶然正しい |
| 未払いの請求書を全部見せて | `limit: 100` のみ。歩き出さない | (歩くという懸念も外れ) |

**モデルは私が思っていたより賢く、最後のページへ一発で飛んだ。**
「歩き回る」という懸念も、少なくともこの 2 例では起きなかった。

##### それでも sort を選ぶ理由 (測り直した後の理由)

ページ送りで答えられるのは、**既定の並び順の逆に当たる「一番〜」ただ 1 つだけ**。

`/orders` の既定は受注日の降順なので、最後のページは「一番古い」注文になる。
だが「一番高額」は既定の並びと無関係なので、**最後のページに行っても出てこない**。
実測でもモデルは `offset: 20` と刻み始め、見えた 40 件の中の最大を答えた
(値が偶然正しかっただけで、根拠は成立していない)。

`sort` なら、どの列の「一番〜」も 1 リクエストで答えが**最初の行に来る**。
加えて、ページ送り方式は「既定の並び順が何か」をモデルが知っている前提に乗る。
暗黙の契約より、明示の引数のほうがよい。

→ **`offset` は画面 (人間) には出し、Tool (LLM) には出さない**という結論は変えない。
ただし理由は「歩き回るから」ではなく
**「1 種類の並びしか答えられず、それ以外では部分的な結果から答えてしまうから」**である。

**列は enum で固定する。** 定義に無い列は GBNF が許さないので生成できない。
`ambiguity` ガードと同じで、指示ではなく到達不能にする。

#### sort と order を 2 つの引数にしたのは失敗だった

最初は `sort=total_amount` + `order=desc` の 2 引数にした。実測すると
モデルは **`sort=total_amount` だけを指定してきた**。向きが無い。
このとき何が起きるかは「既定の列の既定の向き」に依存し、
たまたま DESC だったので正解になった。**運で当たっていた。**

1 つの enum (`total_amount_desc`) に畳んで、
**向きの無い状態そのものを作れなくした。** 畳んだ後は
`sort=total_amount` は許可リストに無い値として既定へ落ちる。

#### 並べ替えを入れるならページ送りの安定性が要る

`ORDER BY ordered_at ASC` だけだと同日の注文の並びが不定になり、
ページ送りしたときに**同じ行が 2 回出たり、どのページにも出なかったりする**。
`svc.OrderBy` は必ず主キーで tiebreak する。ユニットテストで固定した。

許可リストの検証はサービス側にも置いた。LLM は enum で縛られているが、
**API は直接叩ける**。`sort=1;DROP TABLE orders` は許可リストに無いので
既定へ落ちる (実測で確認)。

#### 並べ替えられる列は「モデルに見えている列」に限る

見えない列で並べると「一番古い」と言われても検算できない。
そのため `shipping.search` の projection に `shipped_at` を足した。
これが無いと出荷を日付で並べても、根拠が結果に現れない。

#### 性能

インデックスは張っていない。注文 50,011 件で:

```
Limit (actual time=11.964..11.974 rows=100)
  ->  Sort  Sort Method: top-N heapsort  Memory: 32kB
        ->  Seq Scan on orders (rows=50011)
```

全走査 + top-N heapsort で 12ms。並べ替えなしと変わらない
(12.8ms → 12.6ms)。この規模では不要と判断した。
100 万件では `(ordered_at, order_id)` の複合インデックスが要る。

#### 画面にも同じ欠陥があった

サービスが 1 ページしか返さなくなった時点で、画面も 50,011 件を
新しい順に 25 件ずつ見るしかなくなっていた。**LLM だけ直して人間を
放置するのは筋が通らない**ので、列見出しでの並べ替えも入れた。
画面が持つのはサービスの enum の値そのもので、
向きと列を画面側で組み立て直さない (同じ失敗を繰り返さないため)。

#### 結果

| 質問 | 導入前 | 導入後 |
|---|---|---|

### モデルの thinking を有効にするとどうなるか (2026-09-02)

nlops は既定でモデルの思考を止めている (`reasoning_effort: none` +
`chat_template_kwargs.enable_thinking: false` の両方)。有効にしたらどうなるかを測った。
比較用に `-thinking` を足してある (既定 false、通常運用は変わらない)。

#### 単発では「使える」ように見えた

初手の Tool 選定 1 回だけを、小さなスキーマ (3 プロパティ) で叩くと:

| 設定 | completion tok | 時間 | 結果 |
|---|--:|--:|---|
| OFF (既定) | **65** | 1.8s | `order.countByStatus` |
| ON / max_tokens=512 | 512 で打ち切り | 6.9s | **content 空** |
| ON / max_tokens=1024 | 1024 で打ち切り | 14.0s | **content 空** |
| ON / max_tokens=2048 | **1,453** | 20.1s | `order.countByStatus` (同じ) |

ここで「[result.md](result.md) §5.5 の『reasoning が止まらず content が空』は
**単に予算不足だった**」と結論しかけた。実際、手で選んだ 2 ケースでは
既知の欠陥が両方とも消えた (D22 の禁止 Tool 回避、`status: PLACED` の混入が無くなり
「高橋みどりさんの一番古い注文」が O-1009 → **O-1010 正解**に)。

**この 2 件で判断していたら間違えていた。**

#### 59 ケースで測ると逆だった

`ambiguity` / `cross_service` / `ordering` / `read_ambiguity` の 59 件:

| | 総合 | 平均ms | prompt tok | 失敗 |
|---|--:|--:|--:|--:|
| thinking OFF | **98%** | 4,974 | 8,394 | 1 |
| thinking ON (max_tokens 2048) | **78%** | **24,833** (5.0×) | 10,372 | 13 |

**13 件中 10 件が `max_tokens 到達 (2048 tok)` で content 空。**
D22 も thinking ON で失敗しており、単発で「直った」ように見えたのは再現しなかった。

#### 予算をどこまで上げれば足りるのか

**当初「予算の問題ではない」と書いたが、4096 までしか試さずにそう結論していた。**
指摘を受けて上げ続けた (`n_ctx` は 65,536 あるので余裕はある)。

同じ失敗ケース群を、予算を倍々にして流し直した結果:

| max_tokens | 通過 | 平均ms |
|--:|--:|--:|
| 2048 | 59 件中 13 失敗 (うち 10 が content 空) | 24,833 |
| 4096 | 上記 10 件のうち **4/10** 通過 | 75,517 |
| 8192 | 上記 6 件のうち **2/6** 通過 | 91,968 |
| 16384 | D15 単体 → **通らない** | **234,011** |

**両方が正しかった。** 失敗の多くは確かに予算で解ける (10 → 6 → 4 と単調に減る)。
しかし**残る一群はどこまで上げても終わらない**。

決定的なのは D15「まだ届いていない注文を出して」の単体実行:

```
max_tokens=16384 / prompt 992 tok / 1 コール / 234 秒 → content は空のまま
```

既定の **32 倍**の予算を 4 分近く使って、992 トークンのプロンプトに対して
JSON を 1 つも出せない。しかも step 1 なので履歴は伸びていない。

小さなスキーマ (3 プロパティ) の単発なら 1,453 tok で終わるのに、
Loop の実スキーマ (24 Tool + 画面定義の `anyOf`) では終わらない。
**文法の複雑さと思考が干渉している**という仮説が立つが、切り分けは未了。

実用の観点では、予算で解ける側も安くはない。4096 で平均 76 秒、8192 で 92 秒。

#### §5.5 の仮説は狭すぎた

result.md §5.5 は gpt-oss 20B の 12% を「harmony 形式と制約デコードの相互作用」と
推定していた。**Gemma 4 12B でもまったく同じ症状が出た**ので、
harmony 固有ではない。**思考 + 制約デコード + 実スキーマ**の組み合わせの問題である。

#### 実装の欠陥を 1 つ見つけた

`finalAnswer` が `MaxTokens: 512` を直書きしており、`opt.MaxTokens` を無視していた。
thinking を有効にすると reasoning が枠を食い切り、**最終回答だけが空**で返る。
Loop は成功しているので**回答が消えたことに気づきにくい**。
下限 512・上限は Loop と揃える形に直した (既定では挙動不変)。

#### 結論

**既定 (thinking OFF) を変えない。** 精度が 98% → 78% に落ち、レイテンシは 5 倍、
主要な失敗は「JSON が出てこない」であり、業務用途では最悪の壊れ方をする。

思考が効く場面が無いわけではない (単発では欠陥が 2 つとも消えた) ので、
**制約デコードと両立させる方法**が見つかれば再検討の余地はある。
例えば思考を別の呼び出しに分け、制約付き生成は思考なしで行う 2 段構えなど。未検証。

#### 画面から切り替えられるようにした

「遅い・精度が落ちる」は平均の話であって、個別の問い合わせでは効くこともある
(実測でも単発 2 件では欠陥が消えた)。既定を変えないまま**試せる**ようにした。

- `POST /api/ask` に `thinking` を追加。要求ごとに切り替わる
- アシスタント画面にトグル。何が起きるかを添えてある
  (「モデルに思考させる（遅くなり、精度は落ちます）」)
- 思考を有効にすると 1 反復あたりの上限を 512 → **8192** に上げる。
  512 のままだと reasoning が枠を使い切り、
  **切り替えたら必ず壊れる**ように見えてしまう

実装上、思考の設定は `llm.Client` ではなく `llm.Request` 側で行う。
クライアントは 1 つを共有しているので、`DisableThinking` を触ると
同時に走る他の要求まで巻き込む。

**Intent Gate には思考を入れない。** 出力は 1 文字 (`n`/`t`/`w`) で
`max_tokens` が 16 しかなく、有効にすると必ず枠を使い切って空になる。
逆に**最終回答の生成には入れる** — ここは `response_format` を使わないので、
制約デコードとの干渉が無い唯一の呼び出しになる。

クリーンな条件での実測 (画面と同じ経路):

| 問い合わせ | OFF | ON |
|---|--:|--:|
| 未払いの請求書は何件ありますか | 4.5s / 104 tok | 9.7s / 499 tok |
| 一番古い注文はどれですか | 7.3s / 238 tok | 18.6s / 1,121 tok |

どちらも答えは同じ。**遅くなった分の見返りは、この 2 例では無い。**

### 更新の二重実行を止める (2026-09-02)

#### まず二重実行できることを確かめた

同じ操作を 2 回送ってみた:

| 操作 | 1 回目 | 2 回目 |
|---|---|---|
| `order.cancel` | 200 | **409**「既にキャンセル済み」 |
| `customer.updateContact` | 200 | **200** |

`order.cancel` を止めているのは**サービスの業務ルール**であって BFF ではない。
状態が変わる操作はたまたま弾かれ、変わらない操作は素通りする。
**弾けるかどうかが操作ごとに違うのは、防いでいるとは言えない。**

現在の 3 コマンドはすべて冪等 (絶対値指定) かサービスに守られているが、
それは設計の結果ではなく偶然である。差分で加算する操作を 1 つ足した瞬間に壊れる。

#### 止めるのは一意制約。事前の確認ではない

「実行済みか確認してから実行する」では、**同時に来た 2 本が両方とも
『まだ無い』を見て両方実行する**。監査表の `idempotency_key` に部分一意索引を張り、
**実行前に枠を確保 (INSERT)** し、完了時に結果で更新する形にした。
記録先と排他の置き場所を分けると、記録が入る前に 2 本目が走れてしまう。

実測 (同じ鍵で 8 本同時):

```
実行:     1 回
重複拒否: 7 回
```

2 回目以降は再実行せず `{"ok":true,"alreadyExecuted":true}` を返す。
前回が失敗していればその理由を、実行中なら 409 を返す。

#### 鍵は「この承認」を指す

優先順は ① `Idempotency-Key` ヘッダ ② `traceId + 操作 + 引数のハッシュ`。

**`traceId` が無ければ鍵を作らない。** 会話が無い直接呼び出しでは、
二重送信と「同じ操作をもう一度やりたい」を区別できない。
**区別できないものを勝手に止めるほうが害が大きい。**

引数までハッシュに含めるのは、同じ会話で対象や値を変えた 2 回目を
別の操作として通すため。実測で 4 通り (同一 / 引数違い / 会話違い / 会話なし) を確認した。

#### 途中で 2 つ踏んだ

1. **部分一意索引には `ON CONFLICT` にも同じ述語が要る。**
   `ON CONFLICT (idempotency_key)` だけでは
   「一意制約が見つからない」で全件 503 になった。
   `ON CONFLICT (idempotency_key) WHERE idempotency_key IS NOT NULL` が正しい。
2. **`command_executions.trace_id` の外部キーを外した。**
   監査は best-effort (書けなくても操作は止めない) と決めてあるのに、
   FK があると**トレース記録が落ちただけで更新が実行できなくなる**。
   実行の記録のほうが、会話との紐付けより優先度が高い。

放置された「実行中」の枠は 2 分で引き継げるようにした。
プロセスが落ちたときに、その操作が二度と実行できなくなるのを避けるため。

### 監査に「更新前の値」を残す (2026-09-02)

実行後の状態しか残していなかったので、**何がどう変わったかを後から追えなかった**。

読み取り先は `catalog/commands.json` の `before` で**宣言する**。
更新 API のパスから機械的に導けそうに見えるが
(`PATCH /customers/{id}/contact` → `GET /customers/{id}`)、
規則が崩れた瞬間に静かに誤った値を記録することになる。
**記録が誤っているのは、記録が無いより悪い。**

3 つの判断:

- **失敗しても実行は止めない。** 監査を厚くするための読み取りであって、
  更新の前提条件ではない。ここで止めると
  「記録を良くしたら操作ができなくなった」ことになる
- **実行ユーザーの権限で読む。** その人が見られない情報は監査にも残らない。
  監査だけ権限を越えて読むと、**監査ログが情報漏洩の経路になる**
- **API の封筒 (`data` / `meta` / `_links`) は剥がす。** 必要なのは業務データの
  中身であって、その場限りの trace_id ではない。残す量が増えるほど変化を見つけにくい

実測: `takahashi.m@west.example.com` → `changed@test.example.com` が
1 行に並んで残り、保存サイズは 563 バイト。

### 監査の保持期間 (2026-09-02)

`-audit-retain-days` を足した。**既定は 0 (無制限)。**
黙って消えると「記録が無い」のか「消した」のか区別がつかないので、
消す設定は明示させる。

消す対象は 2 つで扱いを変えた:

- `traces` / `trace_steps` — 会話の記録。量が多く、ゴールデンセットの材料に
  しか使わないので期限で消してよい
- `command_executions` — **業務データを変えた事実**なので会話より長く残す (12 倍)

起動時と 24 時間ごとに実行し、消した件数をログに出す。cron を別に用意させない。

### keyset (cursor) ページング (2026-09-02)

offset は指定分を読み飛ばすので深いページほど遅い。実測 (注文 50,011 件 / 100 件ずつ):

| 方式 | 1 ページ目 | 深い位置 |
|---|--:|--:|
| offset | 12.6ms | **50.5ms** (offset=49,900) |
| cursor | 12.1ms | **9.6ms** (2025-06-01 以降を直接指定) |

**cursor は深さに依存しない。** 5 ページ辿っても 13.4ms のままだった。

#### offset を消さずに併存させた

cursor には「500 ページ目へ飛ぶ」ができない。画面の `TablePagination` は
任意のページへの移動を出すので、**用途が違う**。

- 画面 → `offset` (`MaxOffset` で上限を置く)
- 順に辿る用途 → `cursor`

両方指定された場合は cursor を優先する。

#### 並び順が変わった cursor は捨てる

cursor には**どの並び順で作ったか**を入れてある。受注日順で作った cursor を
金額順のクエリに渡されると、飛ばす行と返す行が噛み合わず、
**静かに歯抜けの結果を返す**ことになる。復元時に照合して、違えば無効にする。

#### 型を持たせる必要があった

cursor の値は JSON を経由するので文字列や float になる。列の型が分からないと
`date > text` のような比較を組み立ててしまう。`Sortable` を
`map[string]Sort{Col, Desc, Type}` に変え、比較時に列の型へキャストするようにした。

同時に、並び順を文字列 (`"ORDER BY ..."`) ではなく構造 (`Order`) で持つよう変えた。
文字列にしてしまうと keyset の比較式を組み立てられない。

行値比較 `(col, pk) > (v, id)` は `ORDER BY col, pk` に対応する。
**列と tiebreak の向きが揃っていることが前提**で、これは
`Order` が両方に同じ向きを使っているから成り立っている
(ページ送りのために入れた tiebreak が、ここで効いた)。

#### 途中で 1 つ壊した

非 cursor 経路から `OFFSET` を落としてしまい、`offset=6` が 1 ページ目を
返すようになっていた。cursor 3 ページと offset の結果を突き合わせて気づいた。
**新しい経路を足すときは、古い経路が同じ答えを返すことを並べて確かめる。**

#### 総件数は cursor でも払っている

`count(*)` は絞り込みの有無に関わらず全走査 (5 万行で 464 buffers)。
しかも**ページごとに毎回**。cursor で行の取得を速くしても、ここは残る。

`?count=none` を足して外せるようにした (既定は数える。
「何件ありますか」に答えられなくなるほうが困る)。
実測で 14.5ms → 10.6ms (28% 減)。5 万件では小さいが、
**1M 件では count が支配的になる**。総件数を返す設計は、
ここにコストを固定しているという自覚が要る。

### UI をモバイルで使えるようにする (2026-09-02)

「PoC にしても UI が酷すぎる。モバイルでヘッダーのページが埋もれるし
スクロールもできない」という報告から。

#### MUI Toolpad は採用しなかった

指示は Toolpad を使うことだったが、**実際に組んで動かした結果として見送った**。
`@toolpad/core@0.16.0` が要求するのは `@mui/material ^7` / `react-router ^7` で、
このプロジェクトは 9.4 / 8.3。2 メジャー差がある。

375px のヘッドレス Chrome で実測した内容:

- `React does not recognize the 'alignItems' prop on a DOM element` が毎レンダリング。
  Toolpad 内部が MUI 7 前提の props を MUI 9 のコンポーネントへ渡し、DOM まで漏れている
- `You are loading @emotion/react when it is already loaded.`
- `@mui/system` が **7.3.11 と 9.4.0 の 2 版**入る。Toolpad が
  `@mui/x-data-grid@8` / `@mui/x-date-pickers@8` を**通常依存**で引くため、
  peer 警告として握り潰せない
- `AppProvider theme={...}` を渡してもテーマが貫通しない
  (`PageContainer` の h1 が MUI 7 既定の Roboto、Button の border-radius が 4px)
- **そもそも報告された問題が直らない。** Toolpad 自身の `DashboardLayout` の
  ヘッダーが 375px 幅で 381〜387px 溢れていた

素の MUI 9 で同じもの (デスクトップは permanent Drawer、モバイルは
temporary Drawer + ハンバーガー) を作るほうが健全と判断した。

#### 本当の原因は 2 つだった

1. **`<Box component="main">` に `minWidth: 0` が無かった。**
   flex の子は既定で中身の幅まで広がるので、表があると body に横スクロールが出る。
   「スクロールもできない」の実体はこれ (横に伸びた body の中で縦スクロールが迷子になる)。
2. **Drawer の先頭に `<Toolbar />` スペーサが無かった。**
   固定ヘッダーの下に「アシスタント」が潜って押せない。
   報告された「ページが埋もれる」がそのまま再現した。

表は潰さない。`Table` に `minWidth` を与えて `TableContainer` の中だけを流す。
潰すと注文 ID が `O-` / `1003` に改行されて読めなくなる。

#### 検証は実際に描画して行った

375 / 414 / 1280px × 全 4 画面で `document.scrollWidth == clientWidth` を確認し、
コンソールの error / warning を 0 にした。SSE も実走させ、
画面遷移と提案カードが 375px で破綻しないことを見ている。

#### 検証手順に穴があった

`pnpm exec tsc --noEmit` を型検査の根拠に使っていたが、
**このプロジェクトでは何も検査していなかった。**
`tsconfig.json` が `files: []` + `references` の solution 形式なので、
`-b` 無しの `tsc` は常に exit 0 を返す (`export const x: number = 'a'` を
置いても通ることを確認)。

実際に型を見ていたのは `pnpm build` (内部で `tsc -b`) と
`vp lint` (`typeCheck: true`) のほうだった。
罠なので `pnpm typecheck` (= `tsc -b`) を用意した。

### 頼まれていない絞り込み — 構造では防げなかった (2026-09-02)

「高橋みどりさんの一番古い注文は？」に対して `status: PLACED` を勝手に足し、
SHIPPED の注文を除外して別の答えを返す失敗 (2/2 再現)。
氏名は 1 件に絞れており、並べ替えも正しく使えている。誤りは足した条件だけ。

これまでのガード (`UnresolvedIDs` / `AmbiguousIDs`) は**値の出所**を見て決まった。
だがここでは決まらない。「未発送の注文」→ `status=PLACED` は**正しい推論**で、
出所を見ても良し悪しが分かれない。

#### 試した機構: 根拠を引用させ、Executor が裏取りする

役割分担としては筋が通っていた:

- 言葉の対応付け (「未発送」→ PLACED) は**言語の仕事**なのでモデルに任せる
- 「その言葉が本当に入力にあったか」は**文字列照合**なので Executor が決める

`status` / `region` / `period` を設定するときは、根拠になった利用者の言葉を
`evidence` に引用させ、それが入力の部分文字列かを照合するようにした。
捏造した引用は照合で落ちる。

**狙ったケースは直った。**

```
order.search {"customer_id":"C005","sort":"ordered_at_asc","status":"PLACED"}
  evidence={"status":"searching_orders"}
  → unjustified_filter: 引用 "searching_orders" は利用者の入力に無い
order.search {"customer_id":"C005","sort":"ordered_at_asc"}
  → O-1010 / 2026-08-18  正解
```

#### しかし正当なケースを壊した

「西日本の顧客は何件ありますか」が**完全に失敗した**。
利用者が明示した `region=WEST` なのに、モデルが根拠を書けず差し戻され、
同じ呼び出しを 5 回繰り返して力尽きる。

モデルが実際に出した `evidence` を見ると、原因ははっきりしていた:

| 入力 | 設定した引数 | モデルが書いた evidence |
|---|---|---|
| 西日本の顧客は何件ありますか | `region: WEST` | `{"status": "searching"}` |
| 西日本の顧客は何件ありますか | `region: WEST` | `{"status": "The user asked for the '"}` |
| 高橋みどりさんの一番古い注文は？ | `status: PLACED` | `{"status": "searching_orders"}` |
| 未発送の注文は何件ありますか | `status: PLACED` | `{"status": "error"}` |

**設定した引数と違うキーに書き、内部メモのような英語を入れ、
日本語の入力を一度も引用していない。** 説明を強めても変わらなかった。

Gemma 4 12B にとって `evidence` は「引用の義務」ではなく
「自由に書ける余白」だった。**機構の設計ではなくモデルの能力で失敗した。**

→ 撤去した。正当な絞り込みを壊す代償に見合わない。

#### 防げないので見せる

構造で防げない以上、**人間が気づける形にする**しかない。
Loop が実際に適用した絞り込み条件を Trace に集め、
SSE の `done` で返し、画面に出すようにした。

| 入力 | 表示される絞り込み | 判定 |
|---|---|---|
| 西日本の顧客は何件ありますか | `region = WEST` | 妥当 |
| 高橋みどりさんの一番古い注文は？ | `status = PLACED` | **頼んでいない** |

回答本文は今も間違ったままだが、
**「一番古い注文」と聞いたのに status で絞られている**ことは人間なら一目で分かる。
差し戻されただけの条件は含めない (使っていない条件を見せても混乱するだけ)。

これは解決ではなく緩和である。**未解決として残す。**

#### 副産物: 曖昧性ガードの誤検知を 1 つ直した

検証の途中で、並べ替えを指定して取った先頭行にも
`ambiguous_id` が出ることが分かった。
「一番古い」と言われてその順に並べ、先頭を取ったのなら**一意に定まる**ので、
これは誤検知。並べ替えを明示した検索の先頭行だけ対象から外した
(2 行目以降は依然として恣意的な選択なので対象のまま)。

### 画面遷移を「提案」にした (2026-09-02)

これまで LLM が画面遷移を選ぶと**即座に飛んでいた**。180 ケース中 33 件が
この経路なので、3 割弱の問い合わせで会話が視界から消えていたことになる。
直前に足した「使われた絞り込み」も、飛んだ先では見えない。

更新操作 (§13) と同じ形に揃えた。**LLM は提案し、移動するかは人間が決める。**
アシスタント画面に遷移先・絞り込み・理由を出し、ボタンで初めて移動する。

#### ボタンだけ足すと手間が増えるだけになる

画面遷移は Tool を 1 つも実行しない (それが速さの理由。1.3 step)。
そのままでは「どの画面を開くか」しか出せず、**遷移せずに済む材料が無い**。
それではボタンを 1 つ増やしただけになる。

BFF が遷移先の**件数と先頭 5 件**を返すようにした。

```
顧客 / region = WEST / 該当 2,503 件
  C004  田中次郎    WEST / ACTIVE
  C005  高橋みどり  WEST / ACTIVE
  C006  伊藤健      WEST / INACTIVE
  …先頭 5 件のみ表示しています。残りは画面で確認してください。
```

「3 件なら開かずに済む、2,503 件なら条件を足す」という判断が、
移動する前にできるようになる。

#### 要約は機械的に作る。LLM には書かせない

サービスの応答をそのまま整形する。LLM に要約させると:

- 遷移経路の速さ (Tool 実行なし) を失う。LLM 呼び出しが 1 回増える
- **見ていないものを書く余地**が増える。この PoC では
  ダミーの値をそのまま答えに使う失敗も、頼まれていない条件を足す失敗も
  実測している

追加コストは実測で **1.5〜7ms** (要約用の API 呼び出し 1〜2 回)。
SSE 全体では 1.9〜2.3 秒で、体感は変わらない。

行数を 5 に抑えているのは、増やすほど画面と同じものを 2 か所で描くことになり、
「遷移するかどうかの判断材料」という役割から離れるため。

#### 要約は実行ユーザーの権限で作る

見えない範囲を教えると、**画面には出ない情報を要約として漏らす**ことになる。実測:

| ユーザー | 顧客一覧の要約 |
|---|---|
| admin | 5,006 件 / 田中太郎・佐藤花子・鈴木一郎… |
| 東日本営業 | 2,503 件 / 田中太郎・佐藤花子・鈴木一郎… |
| 倉庫 | **要約を返さない** (参照権限が無い) |

倉庫ロールでは `summary` を**入れない**。0 件として返すと「該当なし」と
区別がつかず、「顧客は 0 件です」と読めてしまう。
