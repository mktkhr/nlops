# 誤った Tool を踏んだ後の回復挙動

## 問い

スケール検証 ([scale-report.md](scale-report.md)) が測ったのは
**「ダミー Tool を選ばないこと」**だった。504 Tool でも Gemma 4 12B は 100% 正しく選ぶ。

しかし選定精度が高いせいで誤選択が自然発生せず、
**選んでしまった後に何が起きるかを一度も観測していなかった。**
実運用では必ず起きる。「選ばない」で塞げるのは確率であって、経路ではない。

## 方法

誤選択と回復を切り離して測る必要がある。そこで:

1. `loop.Options.ForceFirst` を追加し、**step 1 に誤った Tool を強制的に踏ませる**。
   履歴の形はモデルが自分で選んだときと揃える (assistant の JSON + tool_result)。
   検証専用の計測器で、通常運用では使わない。
2. `eval/cmd/decoystub` — ダミーサービスの応答を返すスタブ。
3. `eval/golden/recovery.json` — 16 ケース。実サービスと責務が隣接するダミーを
   ペアにする (受注↔発注 / 請求↔仕訳 / 在庫↔倉庫作業 / 出荷↔輸送計画 など)。
4. `eval/cmd/recovery` — 回復・汚染・浪費を採点する。

### ダミーの壊れ方を 3 通り作り分けた

これまでの検証ではダミーの `base_url` を誰も listen していなかった。
つまり**選んだ場合は必ず接続エラー**になる。
**実運用のダミーは応答を返す。** 購買サービスは実在し、発注書を返す。
それは受注ではないというだけで、形は整っている。

| mode | 内容 |
|---|---|
| `down` | 接続不可。これまでの検証と同じ状態 |
| `error` | 404 を返す。Tool は在るが対象が無い |
| `plausible` | **Tool 定義の fields どおりの、形の整った別ドメインのデータ**を返す |

`plausible` が本命。Projection を通過するので、LLM から見ると
正しい Tool の結果と区別がつかない。ダミーの値は 9 万番台にして
実データ (C001 / O-1001 / INV-2001) と衝突させ、
最終回答に混ざったら検出できるようにした。

## 結果

Gemma 4 12B / 124 Tool (実 24 + 手書きダミー 100) / 16 ケース。

| ダミーの壊れ方 | n | 正 Tool へ回復 | 画面遷移へ回避 | **汚染** | max_steps 到達 | 平均step |
|---|--:|--:|--:|--:|--:|--:|
| down | 16 | 13 (81%) | 3 | **0 (0%)** | 1 | 3.5 |
| error | 16 | 11 (69%) | 3 | **0 (0%)** | 1 | 3.2 |
| plausible | 16 | 10 (62%) | 3 | **2 (12%)** | 1 | 3.1 |

「回復」は期待する実 Tool に到達したもの、「画面遷移へ回避」は
Tool には戻らなかったが `/orders?customer_name=…` 等の正しい画面を返したもの。
**利用者から見ればこれも正解**なので、両者を足した 13〜16 件 (81〜100%) が
「誤った答えを出さずに済んだ」件数になる。

### 結論 1: 危険なのは、間違った Tool が**成功する**ときだけ

接続不可 (`down`) と 404 (`error`) では汚染ゼロ。モデルは素直に別の Tool へ移る。
**エラーは正しく機能する安全装置だった。**

汚染が出たのは `plausible` の 2 件だけ。どちらも「形の整った別ドメインのデータ」を
そのまま答えにしている。

> **R07**「商品 P001 の単価を教えて」→ `pricing.getPriceList` を強制
> → 回答: **「商品 P001 の単価は 90100 です。」**

> **R11**「注文 O-1002 の合計金額はいくらですか」→ `procurement.getPurchaseOrder` を強制
> → 回答: **「注文 O-1002 の合計金額は 90,100 です。」**

どちらも断定形で、根拠の不確かさを示す言葉が無い。
**READ-only であっても、これは誤情報を業務判断に流し込む経路になる。**

### 結論 2: 機序は「サービスに留まる」ことではなく「名前が一致する」こと

最初に踏んだダミーのサービス内に 2 手以上留まった件数:

| mode | 2 手以上留まった | うち汚染 |
|---|--:|--:|
| down | 1 / 16 | 0 |
| error | 2 / 16 | 0 |
| plausible | 2 / 16 | **2** |

**留まること自体は 3 モードで同じように起きる。** R11 は 3 モードすべてで
`procurement.getPurchaseOrder` を 2 回叩いている。違うのはそこで何が見つかるかだった。

- `down` の R11: 何も得られず → `order.get` へ移り**正解**
- `error` の R11: 404 → 「見つかりません」で終了 (安全)
- `plausible` の R11: `total_amount: 90100` が返る → **それを注文の合計金額として答えた**

R07 の軌跡がいちばん分かりやすい:

```
step 1  pricing.getPriceList        → {"currency":"DECOY-currency-1","name":"ダミーname1", ...}
step 2  pricing.getPriceList        → 同上
step 3  pricing.getMarginAnalysis   → {"product_id":"P-90001","unit_price":90100, ...}
step 4  finish                      → 「商品 P001 の単価は 90100 です。」
```

`DECOY-currency-1` や `ダミーname1` という**明らかに異常な値を 2 手ぶん見ておきながら
疑っていない**。そして `unit_price` という**名前が質問と一致した瞬間に採用した**。
要求したのは `P001` なのに返ってきたのは `P-90001` で、この不一致にも気づいていない。

→ **モデルはサービスを責務で区別していない。「答えらしい形をしているか」で区別している。**
Tool の description に責務境界を書き込む設計 (「顧客から受ける注文は扱わない」)
は**選定には効いたが、結果の解釈には効いていない。**

### 結論 3: 「答えられない」と言える場合もある

R13 / R14 は同じ `plausible` 条件でも汚染しなかった。

> R13「顧客 C001 の未収金はいくらですか」→ `accounting.getAccountBalance` を強制
> → 「Tool の結果に含まれていないため、回答できません。」

R13 のダミーが返したのは `balance` であって `outstanding_amount` ではなかった。
**フィールド名が一致しなかったので採用されなかった。** 結論 2 の裏返しになっている。

## 測定上の限界 — 計測器を 2 回直した

正直に書いておく。**この実験の汚染件数は、最初 2 回とも過小報告だった。**

1. 1 回目: ID 文字列しか記録していなかったため、
   R07「単価は **90100** です」を汚染なしと判定した。→ 数値も記録するようにした。
2. 2 回目: 桁区切りを見ていなかったため、
   R11「合計金額は **90,100** です」を取り逃した。→ 正規化してから照合するようにした。

いずれも**危険な側を見落とす方向**の誤りだった。
修正後、過去の全ログを厳しい条件で再走査して他に漏れが無いことを確認している。

その他の限界:

- **n=16 は小さい。** 汚染 2 件は 12% だが、この数字を精度として扱ってはいけない。
  言えるのは「起きる」ことと「機序」まで。
- ダミーのパスは Tool 名から生成しているので、
  `warehouseops.listLocations` と `asset.listLocations` の 1 組だけパスが衝突する
  (100 Tool 中 1 件)。今回のケースはどちらも使っていない。
- 強制するのは step 1 だけ。**途中の手で誤った場合**は測っていない。
- Gemma 4 12B のみ。他モデルは未測定。

## 未対応 — 構造的な防御は入れていない

汚染 2 件はどちらも同じ形をしている:

> **利用者が指定した ID (`P001` / `O-1002`) が、答えの根拠に使った結果のどこにも出てこない。**

これは Executor 側で検査できる。既にある `UnresolvedIDs` (捏造 ID の差し戻し) や
`AmbiguousIDs` (曖昧な対象での更新提案の差し戻し) と同じ family で、
**プロンプトではなく出所の検証**で塞げる。

ただし今回は**検証までで止めてある**。実装すると
「利用者が ID を書かなかった質問」への扱いを決める必要があり、
別の設計判断になるため。
