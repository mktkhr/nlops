| # | 論点 | 状態 |
|---|---|---|
| 1 | ceiling を 35B-A3B(Q4_K_XL) とすることの妥当性 | **決着**: Q4_K_XL と IQ4_XS で差ゼロ。天井は IQ4_XS で足りる |
| 2 | 2 段階ルーティングが PoC 規模で割に合うか | **決着**: 割に合わない。prefix cache を壊すので 1 段階を既定に |
| 7 | 1 段階が破綻する Tool 数 | **モデル依存**。Gemma 4 12B は 504 Tool でも 100%、Qwen 35B-A3B は 304 Tool 付近から崩れる |
| 8 | strict スキーマのコスト | **決着**: 124 Tool で +30%、504 Tool で **+111〜123%**。Executor 側検証へ逃がせば loose のレイテンシは Tool 数にほぼ非依存 |
| 3 | 小型 dense が MoE 35B-A3B を精度タスクで上回るか | **決着**: Gemma 4 12B が 40/40 で最高成績 |
| 4 | context 削減と cache-reuse のトレードオフ | **決着**: 履歴圧縮は禁止。Projection のみで削減する |
| 5 | gpt-oss 20B が Loop で成立しない原因 | **未解決**。harmony 形式と制約デコードの相互作用を疑っている |
| 6 | Projection の精度への寄与 | **未検証**。結果集合が小さくコスト差 (+23% tok) しか観測できていない |

## P15. データ規模の検証

24 Tool・170 ケースまで詰めた時点で、**データが 11 件しかないことに気づいていなかった**。
`max_items` (20) は一度も発火しておらず、Projection の効果も測れていなかった。

- [x] 実運用に近い規模のシードを追加 (`services/schema/bulk/010_bulk_seed.sql`, `make db-bulk`)
      — 顧客 5,006 / 注文 50,011 / 明細 99,906 / 出荷 48,019 / 請求 49,008 / 商品 506
- [x] 既存の C001-C006 / O-1001.. を壊さない設計 (ID は後ろ、日付は古く)
- [x] 姓を意図的に重複させる (「田中」で 252 件) — 曖昧性を測れるようにする
- [x] 名は種顧客 6 人と重ならないようにする — でないと氏名で 1 件に特定する
      前提のケースが成立しなくなる (最初の版はここを外し 13〜14 人の同姓同名を作った)
- [x] サービス側のページング (`svc.ListPage`) — `/orders` の応答 6.98MB → 42KB
- [x] `count` は**該当総件数**を返す。返却行数を入れると
      「何件ありますか」に LLM がページサイズを答える
- [x] Projection が `count` を保持する (`orchestrator/executor`)
- [x] `reason` に `maxLength` — 結果が大きいとモデルが reason へ全行を書き出し
      max_tokens に達して JSON が閉じなかった (実測 3 件)
- [x] 曖昧 ID ガード — 候補が複数ある一覧から拾った ID で更新提案させない
- [x] BFF の顧客名フィルタを絞り込み下ろしへ (`customer_ids`)
      — 一覧同士をメモリで突き合わせる実装は 5 万件で 0 件を返していた
- [x] 画面に該当総件数を出す (ページ送りの `TablePagination` が兼ねる)
- [x] ゴールデンセット 171 件を再測定 — **98.8%** (データ 11 件のときと同率)
- [x] ページ送り (offset) — 画面に `TablePagination`、位置は URL へ。
      **Tool の引数には出さない** (LLM がページを舐め始めるため)
- [x] 並べ替え (`sort`) — 「一番古い注文」に**2 年 7 か月ずれた答え**を返していた。
      列と向きを 1 つの enum に畳んで出す。列は GBNF で固定、サービス側にも許可リスト
- [x] 並べ替えとページ送りの併用 — 主キーでの tiebreak を必須にする
      (無いと同値行がページ間で重複・欠落する)
- [x] 画面の列見出しでの並べ替え — 同じ欠陥が人間側にもあった
- [x] keyset (cursor) 方式 — 深さに依存しない (offset は 12.6→50.5ms、cursor は 12.1→9.6ms)。
      offset は画面のページ移動用に残して併存。並び順が変わった cursor は無効にする
- [x] `?count=none` — `count(*)` は全走査でページごとに毎回払う。外せるようにした (14.5→10.6ms)
- [x] READ 側の曖昧性ガード — 「高橋さんの一番古い注文」(251 人) で
      1 人を黙って選び 2 年 7 か月ずれた答えを返していた。差し戻しに候補件数を
      入れると、モデルは候補を列挙して利用者に選択を求める。`-no-ambiguity-guard` で A/B 可能
- [x] モデルの thinking の効果測定 — 59 件で 98% → 78%、レイテンシ 5 倍。
      予算を倍々に上げると失敗は減るが (10→6→4)、消えない。
      D15 は 16384 tok / 234 秒でも content が空。既定は OFF のまま
- [x] 画面から thinking を切り替えられるようにする (`POST /api/ask` の `thinking`)。
      有効時は 1 反復の上限を 8192 へ。Intent Gate は除外、最終回答には適用
- [ ] 思考と制約デコードの両立 — 思考を別呼び出しに分け、制約付き生成は
      思考なしで行う 2 段構えなど。**未検証**
- [x] 頼まれていない絞り込み — **構造での防止は失敗した**。根拠を引用させて
      Executor が裏取りする機構を作り、狙ったケースは直ったが、
      モデルが引用を書けず (設定した引数と違うキーに英語の内部メモを書く)、
      「西日本の顧客は何件」のような正当なケースを壊したので撤去
- [x] 代わりに、実際に適用された絞り込み条件を画面に出す。
      回答は誤ったままだが、頼んでいない条件が付いていることは人間なら分かる
- [ ] 頼まれていない絞り込みそのもの — **未解決** (緩和のみ)
- [x] 曖昧性ガードの誤検知 — 並べ替えを明示した検索の先頭行は一意に定まるので対象外にした
- [ ] 条件が 2 つある質問 (「田中さんの一番古い注文」) — `order.search` が
      `customer_id` を 1 つしか取らないため、並べ替えでもページ送りでも解けない。
      現状は正しく「特定できません」と返す。**Tool 設計の課題として未解決**
