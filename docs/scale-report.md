# スケール検証結果 (24 〜 504 Tool)

## 問い

元案 §7〜§9 の 2 段階ルーティング (Stage 1 Service Router → Stage 2 Tool Selector) は、
「全 API 定義を context に入れられない」という前提の上に建っている。

24 Tool ではその前提が成立しなかった (1 段階で精度 100% / cache 95〜97%)。
**では何個の Tool で成立し始めるのか。**

## 方法

- 実サービス 5 / 24 Tool に、2 種類のダミーを混ぜて 24〜504 Tool のカタログを作る
  (`catalog/decoys.json` + `catalog/decoys-bulk.json` + `eval/cmd/mkcatalog`)
- ゴールデンセット 40 件の正解は常に実 Tool 側。
  **ダミーを選び始めたら「Tool 数が増えて選定が壊れた」ことになる。**
- 実サービスは**プロンプト全体へ等間隔に分散**させる
  (504 Tool のとき 53 サービス中の position 0 / 11 / 22 / 32 / 43)。
  先頭へ固めると位置の違いが結果に混ざる。
- 計測中はマシンを他作業から空けた。

ダミーは 2 種類あり、役割が違う。

| 種類 | 数 | 役割 |
|---|--:|---|
| 手書き (`decoys.json`) | 10 サービス / 100 Tool | **難易度**。7 つは既存サービスと責務が隣接する (procurement↔order / accounting↔billing / warehouseops↔inventory / pricing↔inventory / contract↔customer / support↔customer / logistics↔shipping) |
| テンプレート生成 (`decoys-bulk.json`) | 45 ドメイン / 450 Tool | **context への圧力**。業務的に既存サービスと競合しないので、強い distractor ではない |

Tool 定義は約 48 tok/Tool で線形に増える (24 Tool = 1548 tok → 504 Tool = 24,363 tok)。

---

## 結果 1: 1 段階の限界はアーキテクチャではなくモデルにあった

`one_stage` / `strict` / tool 的中率:

| Tool 数 | サービス数 | Gemma 4 12B | Qwen3.6-35B-A3B IQ4_XS |
|--:|--:|--:|--:|
| 24 | 5 | 100% | 100% |
| 44 | 7 | 100% | 100% |
| 64 | 9 | 100% | 98% |
| 104 | 13 | 100% | 98% |
| 124 | 15 | 100% | 98% |
| 204 | 23 | 100% | 98% |
| 304 | 33 | 100% | **92%** |
| 404 | 43 | 100% | 95% |
| 504 | 53 | **100%** | **90%** |

- **Gemma 4 12B は 24 → 504 Tool (21 倍) で劣化ゼロ。**
- **Qwen3.6-35B-A3B は 304 Tool 付近から崩れ始め、504 Tool で 90%。**
  40 件中 4 件の取りこぼしで、ノイズでは説明できない。

同じアーキテクチャ・同じプロンプト・同じカタログで、**モデルによって限界が全く違う**。
「何 Tool まで大丈夫か」はアーキテクチャの性質ではなくモデルの性質だった。

これは PoC 本体で見えた傾向 (active 3B の MoE より dense 12B が精度タスクで強い) が、
スケールさせるとさらに開くことを示している。

## 結果 2: 制約は context ではなく文法コスト。そしてそれは回避できる

`anyOf` で Tool ごとに引数スキーマを固定する `strict` と、tool 名だけ enum で拘束する `loose`:

| Tool 数 | モデル | loose ms | strict ms | strict の追加コスト |
|--:|---|--:|--:|--:|
| 24 | Qwen IQ3_S | 394 | 464 | +18% |
| 124 | Gemma 4 12B | 778 | 1031 | +33% |
| 124 | Qwen IQ4_XS | 803 | 1038 | +29% |
| 504 | Gemma 4 12B | **833** | 1756 | **+111%** |
| 504 | Qwen IQ4_XS | **848** | 1888 | **+123%** |

**504 Tool では総レイテンシの半分以上が GBNF 文法のコスト**になる。

そして決定的なのは `loose` の側で、

| Tool 数 | Gemma loose ms | Qwen loose ms | prompt tok |
|--:|--:|--:|--:|
| 124 | 778 | 803 | 約 5,900 |
| 504 | **833** | **848** | 約 23,700 |

**Tool 数を 4 倍にしてもレイテンシはほぼ変わらない** (+7%)。
prompt が 4 倍になっても prefix cache が 97〜100% 効くので prefill が発生しない。

精度差は 504 Tool で Gemma 100%/98%、Qwen 90%/92% (どちらも 40 件中 1 件、ノイズ範囲)。

→ **`loose` スキーマ + Executor 側の引数検証**を使えば、504 Tool 規模でも
レイテンシは実質フラットになる。enum 値の検査は `orchestrator/executor` に実装済み
(`invalidEnums`)。定義外の引数名は元から `sanitizeArgs` が落としている。

## 結果 3: 2 段階が有利になる点はモデルによって違う

| Tool 数 | Gemma 的中 / ms |  | Qwen 的中 / ms |  |
|--:|--:|--:|--:|--:|
| | one_stage | two_stage | one_stage | two_stage |
| 124 | 100% / 1034 | 98% / 2107 | 98% / 1103 | 98% / 1976 |
| 204 | 100% / 1203 | 100% / 2232 | 98% / 1366 | 95% / 1897 |
| 304 | 100% / 1436 | 100% / 2272 | 92% / 1642 | 90% / 1908 |
| 404 | 100% / 1669 | 98% / 2281 | 95% / 1915 | 95% / 1875 |
| 504 | **100% / 1906** | 100% / 2295 | **90% / 2324** | **95% / 1871** |

- **2 段階のレイテンシは Tool 総数に依存しない** (Gemma 2107→2295ms、Qwen 1976→1871ms)。
  Stage 2 が見るのは選ばれたサービスの Tool だけだから。
  一方 1 段階 (strict) は線形に増える。
- **Gemma では 504 Tool でも 1 段階が勝つ** (100% / 1906ms vs 100% / 2295ms)。
- **Qwen では 504 Tool で 2 段階が逆転する** (90% → 95%、2324ms → 1871ms)。

ただしこの比較は `strict` 前提であり、`loose` の 1 段階 (833〜848ms) は
どのモデル・どのサイズでも 2 段階より速い。

## 確定したこと

### 1. 元案 §7〜§9 の 2 段階ルーティングは削除してよい

24〜504 Tool の全域で、`loose` + Executor 検証の 1 段階が
精度・レイテンシとも 2 段階以上だった。
「全 API 定義を context に入れられない」という前提は、prefix cache のある環境では
少なくとも 504 Tool まで成立しない。

§21 の Retrieval (BM25 / Embedding) は、**Tool 数のためではなく精度のために**
検討する対象になった。Qwen のようなモデルを使う場合は 300 Tool 付近から効いてくる。

### 2. 既定構成は「1 段階 + loose + Executor 検証 + dense 12B 級」

| 項目 | 選択 | 理由 |
|---|---|---|
| ルーティング | 1 段階 | 504 Tool まで 2 段階以上 |
| スキーマ | `loose` (Tool 名のみ enum 拘束) | 504 Tool で文法コストが 2 倍以上。精度差なし |
| 引数の検証 | Executor 側 (`invalidEnums` + `sanitizeArgs`) | 文法から逃がしても防御は維持できる |
| モデル | Gemma 4 12B 級の dense | 504 Tool で 100%。35B-A3B は 90% |

小規模 (〜124 Tool) では `strict` のコストが 30% 程度なので、
文法で守れる分は守っておく方が安全。**Tool 数で切り替える**のが正しい。

### 3. スケールしたときに効くのは総パラメータではなく active パラメータ

Qwen3.6-35B-A3B は総 35B だが 1 トークンあたりに通るのは 3B 相当。
Gemma 4 12B は dense 12B。**Tool 数が増えるほど差が開いた** (124 Tool で 2pt、504 Tool で 10pt)。

「精度が足りなければモデルを大きくする」は、MoE では成り立たない。

## 測定上の限界

- **n=40 は小さい。** 1 ケース = 2.5 ポイント。
  読み取ってよいのは Qwen の 98% → 90% (4 件) と、Gemma が全域で落ちなかった事実。
  「98% と 100%」の差は読み取ってはいけない。
- **バルクのダミーはテンプレート生成。** 難易度を担っているのは手書きの隣接サービス 7 つで、
  450 Tool 分は context への圧力にすぎない。
  **実運用で 500 個の Tool が全て互いに紛らわしい場合、結果はこれより悪くなる。**
- **測ったのは Tool 選定であって Loop 全体ではない。** ダミー Tool を選んでしまったときの
  回復挙動は未検証。
- **504 Tool が上限。** それ以上は未測定。
- 24〜124 の系列は実サービスを交互配置、124〜504 の系列は等間隔配置で測った。
  両者が重なる 124 Tool では結果が一致した (Gemma 100% / Qwen 98%) ので、
  配置の違いは影響していないと判断した。
